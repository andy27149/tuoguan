# 机构管理员总览页 —— 设计文档

## 背景

机构管理员现在登录进后台，默认落地在"教师列表"页（`AdminDashboardPage` 的
`activeModule` 默认值是 `'teachers'`）。没有任何一个页面能让管理员一眼看出机构
当前的整体状况——想知道"有没有学生课时快用完了""这个月有没有人没缴费"，得分别
点开消课页、账单管理页自己扒。导航里现有的"任务完成情况"（`AdminTaskStatsModule`
/ `AdminStatsService.getDashboard`）命名上像 dashboard，但其实只统计当天各托管
班的签到数+任务完成度，是运营层面的日常小工具，不解决"机构整体健康度"这个问题。

这次要做一个新的总览页，作为管理员登录后的默认首页，首屏五张卡片：课时不足预
警、账单欠费提醒、在读规模、今日运营快照、收入快照。

> 2026-10-08 补充：静态原型做完让用户看过一版后，发现"账单欠费提醒"和"本月收
> 入快照"（当时还叫这个名字）两张卡片的时间口径有问题，根源都是同一个事实——
> **账单生成是管理员手动触发的，没有定时任务，而且只会在一个月结束之后才有意
> 义去生成**（月中生成的话出勤/用餐天数都不是最终数字）。所以月初查"当月账
> 单"大概率是空的。下面的设计已经按修正后的口径写，不是最初讨论时的版本——
> 决策 4、5 和对应的卡片 2、5 小节都已更新，其余三张卡片不受影响。

## 核心设计决策

1. **定位**：新增 `AdminModule` 值 `'overview'`，作为 `AdminDashboardPage` 的新
   默认值（替换现在的 `'teachers'`），导航里单独成组放在最上面。不是"基础配置"
   下面挂的子项，是独立入口。
2. **架构：每张卡片一个独立的小接口，不做大聚合接口**。沿用现有代码按领域分包
   的方式（course/billing/kanban/roster 各管各的），前端 `Promise.all` 并行拉
   取、每张卡片独立 loading/error 状态，互不阻塞。以后加新卡片不用动已有的。
   五个接口统一挂在新建的 `admin/web/AdminOverviewController`，路径前缀
   `/api/admin/overview/*`——不复用现有 `AdminStatsController` 的
   `/api/admin/dashboard` 路径，那个是"任务完成情况"专用的，概念上跟这次的
   "总览页"是两回事，混在一起容易以后搞混。
3. **课时不足预警复用已有阈值**：`CourseConsumptionPage` 已经定好 `<3` 黄色、
   `<=0` 红色两档，这里直接复用，不做机构可配置的阈值——本次讨论中明确确认的
   取舍，以后如果需要可配置再单独评估。
4. **账单欠费提醒统计所有月份，不限定本月**（修正后的决策，推翻了最初讨论的
   "只看本月"）：账单生成是手动触发、且只会在月份结束后才有意义去生成，月初
   当月账单大概率还没生成，"只看本月"会导致这张卡片在每个月的前段时间基本是
   空的，而真正该被提醒的"以前月份一直没缴费"反而完全看不见。改成不限月份，
   汇总所有"已生成账单但未标记已缴费"的记录，每行标注具体是哪个月欠费，同一
   个学生可能因为好几个月都没缴费而出现好几行。代价是如果管理员线下收了钱却
   忘了去账单管理页把状态改成"已缴费"，这里会一直显示欠费——但这个假设账单
   管理页本身也依赖（账单管理页的"是否已缴费"列就是同一个字段），不算这次新
   增的风险。
5. **收入快照拆成两个不同的时间口径，卡片标题不再叫"本月收入快照"**（修正后
   的决策）：托管费应收/实收依赖账单生成，跟上一条决策 4 同样的原因，只能展
   示**上个月**（比如现在是 10 月，就展示 9 月）的数字，当月的托管费账单八成
   还不存在；课外课消课次数不一样，消课记录是老师每天实时产生的，不依赖"生成
   账单"这个动作，用**本月**到目前为止的实时次数没问题。两个指标分别标注各
   自的月份（"上月托管费"/"本月消课次数"），不再用一个卡片级的日期笼统概括。
   另外，课外课消课次数不把钱算进去——这部分是最初讨论就定下、没有变化的决
   策：消课记录本身不记金额，只有配置了单价（`pricePerLesson`）的课程才能换
   算，强行换算会让"有些课程算了钱、有些没配就不算"的口径不一致问题暴露在这
   张卡片上。
6. **不做"待处理账号事项"**（如未改初始密码的教师账号）——本次讨论中明确排
   除，优先级最低，以后需要再加。

## 五张卡片的数据来源与新增接口

### 1. 课时不足预警

现状：`CourseAccountService.getStatement(institutionId, studentId)` 已经能算
单个学生的课程余额（充值记录 - 消课记录，按学生+课程分组），但只能查一个学生，
没有机构范围的批量查询。`CourseRechargeRecordDao`/`CourseConsumptionRecordDao`
目前都只有 `findAllByStudentId`，没有 `findAllByInstitutionId`。

新增：
- `CourseRechargeRecordDao.findAllByInstitutionId(institutionId)`、
  `CourseConsumptionRecordDao.findAllByInstitutionId(institutionId)` 各一个批
  量查询方法（一次查全机构，不要对每个学生循环查）。
- `CourseAccountService.getLowBalanceEntries(institutionId, threshold)`：拉到
  全机构的充值+消课记录后，按 (studentId, teachingUnitId) 分组算余额（逻辑抄
  `getStatement` 里那段分组代码），过滤出 `balance <= threshold` 的条目，返回
  `List<LowBalanceRow>`，每条含 `studentId, studentName, courseId, courseName,
  balance`。threshold 固定传 3（对应前端 `<3` 黄色这一档；红色 `<=0` 由前端
  根据 `balance` 自己着色，不需要后端分两次查）。
- `GET /api/admin/overview/low-balance` → `List<LowBalanceRow>`，按
  `balance` 升序排（最紧急的排前面）。

### 2. 账单欠费提醒

现状：上一轮刚做的 `BillGenerationService.getBillOverviewAllMonths
(institutionId, null, null, false)` 已经是"机构范围、不限月份、每个
(学生,月份) 一行"的查询，账单管理页在"月份"筛选留空时直接用它的结果渲染表
格。

新增：
- `BillGenerationService.getUnpaidBillSummary(institutionId)`：内部调用
  `getBillOverviewAllMonths(...)`，过滤 `billId != null && !isPaid`，返回
  `UnpaidBillSummary(int count, BigDecimal totalAmount, List<UnpaidBillRow>
  rows)`，`UnpaidBillRow` 含 `studentId, studentName, className, yearMonth,
  totalAmount`（比最初版本多了 `yearMonth` 字段，因为现在同一个学生可能因为
  好几个月都欠费而出现好几行，前端需要知道具体是哪个月）。
- `GET /api/admin/overview/unpaid-bills` → `UnpaidBillSummary`（不接受月份参
  数，就是要汇总所有月份）。

### 3. 在读规模

现状：`StudentDao.findAllByInstitutionId(institutionId)` 已有，`Student` 记录
自带 `enrolled`、`teachingUnitId`（null=纯课外课）。`TeachingUnit` 自带
`teacherId`。不需要新 DAO 方法，纯 Java 里过滤+分组统计。

新增：
- `AdminStatsService.getEnrollmentSummary(institutionId)`：过滤
  `enrolled=true` 后，统计 `totalCount`、`custodyCount`（teachingUnitId !=
  null）、`offCampusOnlyCount`（teachingUnitId == null），再按
  `teachingUnitId` 分组、查教师名，返回按教师分布的 `List<TeacherStudentCount>`
  （`teacherName, studentCount`）。
- `GET /api/admin/overview/enrollment` → `EnrollmentSummary`。

### 4. 今日运营快照

现状：`AdminStatsService.getDashboard` 已经示范了"遍历机构下所有 MONTHLY 教学
单元，每个单元分别查当天签到/任务"的写法（`StudentArrivalCheckinDao
.findAllByTeachingUnitIdAndDate` 等，都是按 teachingUnitId 查，没有机构范围批
量方法）。这张卡片延续同样的写法，不新增 DAO 方法，只是把现在"按班级分别返回"
的粒度在 service 层汇总成机构整体的三个数字。

新增：
- `AdminStatsService.getTodaySnapshot(institutionId, date)`：遍历机构下所有
  MONTHLY 教学单元，累加 `StudentArrivalCheckinDao
  .findAllByTeachingUnitIdAndDate`、`StudentMealRecordDao
  .findAllByTeachingUnitIdAndDate`、`StudentLeaveRecordDao
  .findAllByTeachingUnitIdAndDate` 三者的条数，返回
  `TodaySnapshot(int arrivedCount, int mealCount, int leaveCount, int
  totalCustodyStudentCount)`（分母用在读托管班学生总数，方便前端展示"12/20 已
  到"这种格式）。
- `GET /api/admin/overview/today` → `TodaySnapshot`。

### 5. 收入快照（原名"本月收入快照"，见决策 5 的修正说明）

现状：托管费部分需要查**上个月**（`YearMonth.now().minusMonths(1)`）的账单，
跟"账单欠费提醒"现在用的 `getBillOverviewAllMonths` 不是同一个查询形状了（那
个不限月份，这里要限定到具体某一个月），所以不能再像最初版本设想的那样共用
同一次调用结果，各自独立查一次。课外课消课次数用的是**本月**
（`YearMonth.now()`），复用"课时不足预警"已经新增的
`CourseConsumptionRecordDao.findAllByInstitutionId`，按 `consumptionDate` 落
在本月的过滤计数即可，不用再新增 DAO 方法。

新增：
- `BillGenerationService.getRevenueSnapshot(institutionId)`：内部调用
  `getBillOverview(institutionId, YearMonth.now().minusMonths(1), null, null,
  false)` 算上个月的 `tuitionBilled`（所有有账单的 `totalAmount` 求和）、
  `tuitionCollected`（`isPaid=true` 的 `totalAmount` 求和）；再调用
  `CourseAccountService.countConsumptionsInMonth(institutionId,
  YearMonth.now())` 算本月消课次数。返回
  `RevenueSnapshot(String tuitionMonth, BigDecimal tuitionBilled, BigDecimal
  tuitionCollected, String consumptionMonth, int
  offCampusConsumptionCount)`——`tuitionMonth`/`consumptionMonth` 把实际月份
  （`"2026-09"`/`"2026-10"`）传给前端，前端直接显示这两个字符串，不在前端里
  用"上月"/"本月"这种相对说法硬编码、也不用自己再算一遍是哪个月。
- `CourseAccountService.countConsumptionsInMonth(institutionId, YearMonth
  month)`：复用 `findAllByInstitutionId` 查询结果按月过滤计数。
- `GET /api/admin/overview/revenue` → `RevenueSnapshot`。

## 前端改动范围

- 新增 `frontend/src/api/adminDashboard.ts`：五个接口各一个 fetch 函数 +
  五个对应的 TS 接口（`LowBalanceRow`、`UnpaidBillSummary`、
  `EnrollmentSummary`、`TodaySnapshot`、`RevenueSnapshot`）。
- 新增 `frontend/src/pages/AdminOverviewModule.tsx`：`useEffect` 里对五个
  fetch 函数分别调用（不是包在一个 `Promise.all` 里阻塞成同一个 loading
  state——每张卡片自己的 `data/loading/error` 三态独立），渲染五张卡片。
  "课时不足预警"卡片里每一行点击可以跳到对应学生的"对账单/充值"弹窗（复用
  `AdminCourseStatementModal`，传 `studentId`/`studentName`，跟学生总览页现在
  的用法一样）；"账单欠费提醒"卡片点击可以跳到账单管理页对应学生（这次只做
  "点了切到账单管理模块"，不做深链接到具体学生的筛选，深链接留给以后）。
  具体视觉布局（卡片怎么排、用什么颜色/图标）留到下一步 UI 设计环节，这版只定
  数据和交互，不做样式细节。
- `frontend/src/components/AdminSidebar.tsx`：`AdminModule` 新增 `'overview'`；
  `NAV_GROUPS` 最前面新增一组 `{ label: '总览', items: [{ key: 'overview',
  label: '机构总览' }] }`；`overview` 不受 `custodyEnabled`/`offCampusEnabled`
  任一开关影响，不设 `hiddenWhen`（两种学生身份的数据都展示，不该因为某个开关
  关闭就整页隐藏）。
- `frontend/src/pages/AdminDashboardPage.tsx`：`useState<AdminModule>('teachers')`
  改成 `useState<AdminModule>('overview')`；`main` 里新增一个分支渲染
  `<AdminOverviewModule />`。

## 范围界定 / 不做

- 不做机构可配置的课时预警阈值，固定复用现有 `<3`/`<=0` 两档——本次讨论中明
  确确认的取舍。
- 账单欠费提醒依赖管理员在账单管理页及时维护"是否已缴费"状态，系统不会主动
  核对线下收款——这个假设账单管理页本身也依赖，不是这次新增的风险。
- 收入快照不把课外课消课换算成金额，只展示次数——本次讨论中明确确认的取
  舍。
- 不做"待处理账号事项"（未改初始密码的教师账号等）——本次讨论中明确排除。
- 不做卡片内的筛选/分页/导出，数据量超出一屏按现有页面的习惯处理（比如课时不
  足预警名单很长就自然滚动，不额外做分页控件）。
- 这版只定数据和接口，不涉及视觉设计（卡片排版、配色、图标），UI 设计是下一
  个独立环节。
- 不做告警通知（邮件/短信/站内推送），只是在管理员主动打开总览页时展示当下
  的快照数据。

## 测试策略

- 后端：
  - `CourseAccountService` 新增 `getLowBalanceEntries`/
    `countConsumptionsInMonth` 的单元测试或集成测试（用真实充值/消课记录造场
    景：余额充足的不出现、余额 <3 的出现、余额 <=0 的也出现）。
  - `BillGenerationService` 新增 `getUnpaidBillSummary`/`getRevenueSnapshot`
    的测试（复用现有 `AdminBillOverviewControllerTest` 的机构/账单造数据方
    式）；`getUnpaidBillSummary` 要专门测"同一个学生两个月都欠费，返回两
    行，各自标对月份"这个场景；`getRevenueSnapshot` 要测"当月账单还没生成
    也不影响上月数据正常返回"。
  - `AdminStatsService` 新增 `getEnrollmentSummary`/`getTodaySnapshot` 的测
    试。
  - 五个新 Controller 方法各补一个 `AdminOverviewControllerTest`（新建这个测
    试类，对应新建的 `AdminOverviewController`），覆盖"有数据"和"空机构"两种
    情况，权限上确认非 ADMIN 角色返回
    403/401（照抄现有 admin controller 测试的鉴权断言风格）。
- 前端：
  - `AdminOverviewModule.test.tsx`：五张卡片分别 mock 对应 API，断言数据正确
    渲染；至少一张卡片 mock 成 reject，断言只有这张卡片显示错误、其他四张正
    常渲染（验证"互不阻塞"这条设计决策）。
  - `AdminSidebar.test.tsx` 补充"总览"导航项存在、点击后 `onSelect` 收到
    `'overview'` 的断言。
  - `AdminDashboardPage.test.tsx` 补充默认 `activeModule` 是 `'overview'` 的
    断言（原来测的是 `'teachers'`，这个断言需要相应更新，不是新增）。
