# 学生总览页筛选/分页/新建学生弹窗重设计

## 背景

`AdminStudentsModule.tsx`（学生总览页）目前一次性拉取机构下全部学生，渲染成一张长表格：

- 托管班学生多的时候（比如一个班上百人），表格变成一个很长的列表，没有分页，滑动体验差。
- 没有任何筛选/搜索能力——想找某个学生或者看某个托管老师名下的学生，只能自己在长列表里肉眼找。
- 页面顶部的"新建学生"表单内容越来越多（姓名、学籍班、托管班下拉、课外课多选），挤占了页面顶部的空间，跟下面的学生列表挤在一起。

`账单管理页`（`AdminBillingModule.tsx`）结构类似（也是学生维度的列表），已经有月份/班级/姓名三个筛选，但同样没有分页。

## 现状调研

- `GET /api/admin/students`（`AdminStudentController` → `AdminStudentService.listStudents`）：无筛选参数，返回机构下全部学生，排序逻辑在 `StudentOverviewOrder`（托管学生按托管教师姓名排，纯课外学生按首门课程名排，同组内按姓名兜底排序）。
- `GET /api/admin/bills`（`AdminBillOverviewController` → `BillGenerationService`）：已支持 `month`/`classRoomId`/`studentName`/`offCampusOnly` 四个查询参数做服务端筛选，但筛选后的结果不分页，一次性全量返回。

## 范围

本次设计**只覆盖学生总览页**，具体包括：

1. 筛选：身份（全部/托管/纯课外）、托管教师、姓名模糊搜索，三者为"且"的关系。
2. 分页：固定每页 20 条。
3. 新建学生表单抽成独立弹窗，课外课多选从原生 checkbox 改成可点击的胶囊标签。

**不在本次范围内**（已和用户确认，作为后续工作）：

- 账单管理页补分页——复用本次抽出来的 `Pagination` 组件，但账单页的筛选已经存在、不用动，不在本次实施。
- 后端接口改动——筛选和分页都做成纯前端（在已经拉回来的全量学生列表上用 JS 过滤和切片），`GET /api/admin/students` 接口本身不加任何查询参数，不touch `AdminStudentController`/`AdminStudentService`/DAO 层。原因：当前试运营机构的学生规模还在可以一次性拉全量的量级，等真的出现后端分页的必要性时再单独立项做服务端分页；现在做纯前端方案改动面最小、验证最快。

## 设计：筛选

三个筛选条件，各自是独立的 React state，互相之间"且"的关系：

| 筛选项 | 取值 | 判定字段 |
|---|---|---|
| 身份 | 全部 / 托管 / 纯课外 | `student.offCampusOnly`（false=托管，true=纯课外） |
| 托管教师 | 全部 / 具体某个教师姓名 | `student.teacherName`（纯课外学生这个字段恒为 null，天然不会匹配任何具体教师） |
| 姓名 | 自由文本，模糊匹配 | `student.name.includes(query.trim())`，不区分大小写（中文姓名场景下大小写不重要，但英文名/拼音搜索时统一转小写比较） |

实现细节：

- 托管教师筛选的下拉选项，从**当前已经拉回来的全量 `students` 列表**里按 `teacherName` 去重生成（过滤掉 null），不是从筛选后的子集生成——这样切换身份筛选不会导致教师下拉的选项跟着增减、让用户看着选项列表"抖动"。
- 三个条件任意组合都允许，包括看起来矛盾的组合（比如"身份=纯课外"+"托管教师=王老师"）——纯课外学生的 `teacherName` 恒为 null，这种组合会自然得到空结果，不需要专门写互斥校验逻辑去阻止用户选出这种组合，空状态本身就是正确反馈。
- 姓名搜索框用受控 input，每次按键都立即重新计算筛选结果（不做防抖）——前端全量数据在内存里过滤，当前数据量级下性能没有问题，防抖是不必要的复杂度。

## 设计：分页

- 固定每页 20 条，不加页大小选择器。
- 分页状态是独立的 `currentPage` state（从 1 开始计数）。
- **派生计算架构**（这是跟"编辑/新建后筛选还生效吗"这个问题直接相关的核心设计）：`students`（接口拉回来的全量原始数据）和三个筛选条件、`currentPage` 都是互相独立的 state。真正渲染给用户看的数据，是每次渲染时用 `useMemo` 重新算一遍的派生值：

  ```
  filteredStudents = students.filter(符合三个筛选条件)
  totalPages = Math.max(1, Math.ceil(filteredStudents.length / 20))
  currentPageClamped = Math.min(currentPage, totalPages)
  pageItems = filteredStudents.slice((currentPageClamped - 1) * 20, currentPageClamped * 20)
  ```

  这样设计之后：
  - 新建/编辑/停用学生后，照旧调用现有的 `loadStudents()` 刷新全量 `students`，筛选条件和页码不用任何额外代码就能对新数据重新生效——因为它们本来就是"现算"的，不是保存下来的快照。
  - 如果某次操作导致筛选结果变少、当前页码超出了新的总页数（比如本来在第 3 页，操作后筛选结果只剩 2 页），`currentPageClamped` 会自动把用户带回最后一页，不会出现"第3页但其实什么都没有"的空白页。
  - 如果编辑把某个学生改得不再符合当前筛选条件（比如把"纯课外"身份筛选下的学生转去了托管班），他会从筛选结果里直接消失——这是预期行为，不是 bug，因为筛选本来就是对最新数据实时重算的。
- 修改任意一个筛选条件（身份/教师/姓名）时，**立即把 `currentPage` 重置为 1**——这是标准列表交互惯例：用户去改筛选条件，默认是想从头看新结果，不应该停留在一个对新筛选条件可能没有意义的页码上。
- 分页条 UI：复用的 `Pagination` 组件，接收 `page`/`totalPages`/`onPageChange` 三个 prop，渲染"共 N 条 · 第 X 页 / 共 Y 页" + 上一页/下一页两个按钮（页码到达首/尾时按钮 disabled）。这个组件不知道、也不关心筛选逻辑，只负责"给定总页数和当前页，渲染分页条、上报页码变化"——这样账单管理页后续接入时，只需要在自己的筛选结果上包一层同样的 `useMemo` 切片逻辑，直接复用这个组件渲染分页条。

## 设计：新建学生弹窗

原来挤在页面顶部的"新建学生"表单（姓名、学籍班、托管班下拉、课外课多选）原样搬进一个新的 `CreateStudentModal` 弹窗组件，字段和校验逻辑不变（姓名必填、创建按钮在姓名为空时 disabled），接口调用也不变（成功后关闭弹窗 + 调 `loadStudents()` 刷新列表）。弹窗视觉跟 `AdminCourseStatementModal` 一致：白色圆角卡片、半透明黑色遮罩、`Sora` 字体标题、`#6d5bd0` 紫色主按钮。

课外课多选这部分是本次重新设计的重点，经过静态 HTML 预览（`docs/mockups/admin-create-student-modal-redesign.html`）确认过效果：

- 原来是一排原生 `<input type="checkbox">` + 文字标签，手机上点击区域小、课程一多就换行占用很多垂直空间。
- 改成可点击的胶囊标签（pill button）：未选中是白底灰字描边，选中态是 `#6d5bd0` 紫色填充 + 白字 + 一个小勾选图标，点击整个标签切换选中状态（不是只能点中间那个 14x14 的 checkbox）。
- 标签外层包一层 `max-height: 150px` + `overflow-y: auto` 的容器，课程数量不管多少，弹窗本身的高度都不会被撑大——容器内部出现滚动条即可。
- 标题行右侧加一个"已选 N 门"的实时计数，不用数标签颜色就知道选了几个。

## 组件结构与文件布局

本次只涉及前端，不改后端。新增/修改的文件：

- **新增** `frontend/src/components/Pagination.tsx`：通用分页条组件，props 为 `{ page: number; totalPages: number; onPageChange: (page: number) => void; totalItems: number }`，渲染"共 N 条 · 第 X 页 / 共 Y 页"+上一页/下一页按钮。不感知具体业务数据，纯展示+回调。
- **新增** `frontend/src/components/CreateStudentModal.tsx`：承接原来页面顶部的新建学生表单，props 为 `{ classRooms: TeachingUnit[]; offCampusCourses: TeachingUnit[]; onCreate: (name, schoolClassName, teachingUnitId, courseIds) => Promise<void>; onClose: () => void }`，内部自己管理表单字段 state、提交中/错误提示 state。
- **修改** `frontend/src/pages/AdminStudentsModule.tsx`：
  - 移除原来内联的新建学生表单 JSX，改成一个"+ 新建学生"按钮 + 条件渲染 `CreateStudentModal`。
  - 新增筛选工具条：身份下拉、托管教师下拉、姓名搜索框。
  - 新增 `identityFilter`/`teacherFilter`/`nameQuery`/`currentPage` 四个 state。
  - 新增 `filteredStudents`/`pageItems`/`totalPages` 三个 `useMemo` 派生值（如上文分页小节的计算逻辑）。
  - 表格的数据源从 `students` 改成 `pageItems`；表格下方渲染 `<Pagination />`。
  - 不改动已有的编辑/停用/启用逻辑和对应的 API 调用。
- **测试**：新增 `Pagination.test.tsx`、`CreateStudentModal.test.tsx`；更新 `AdminStudentsModule.test.tsx` 覆盖筛选组合、分页边界、筛选后页码收缩、弹窗联动这几类用例。

## Review Focus（最容易被漏测的几个点）

1. **筛选后页码收缩**：在筛选结果有 3 页时翻到第 3 页，然后改变筛选条件（或编辑/停用某个学生）使结果只剩 2 页——断言自动收缩到新的最后一页（第 2 页），而不是停留在第 3 页显示空白、也不是无条件跳回第 1 页（页码收缩的目标是"新的最后一页"，不是恒定的"第 1 页"——两者在"只剩 1 页"这种特殊情况下刚好重合，容易被误写成"收缩后永远回第 1 页"，写用例时要用一个会收缩到非 1 页码的例子才能测出这个区别）。
2. **编辑导致学生从当前筛选结果消失**：身份筛选="纯课外"时编辑一个学生、把他转成托管班学生，保存后断言这个学生从当前筛选列表里消失（且不报错）。
3. **矛盾筛选组合产生空结果**：身份="纯课外" + 托管教师=某个具体老师，断言列表为空、不报错、不崩溃。
4. **新建/编辑后筛选条件保持生效**：设置好筛选条件后新建一个不匹配筛选条件的学生，断言新学生不出现在当前筛选视图里（因为筛选是对全量数据实时重算的）；新建一个匹配筛选条件的学生，断言他确实出现在列表里。
5. **分页条边界状态**：只有 1 页数据时，上一页/下一页按钮都应该是 disabled；在第 1 页时上一页 disabled，在最后一页时下一页 disabled。

## 后续工作（不在本次实施范围）

- **账单管理页接入分页**：复用本次抽出来的 `Pagination` 组件。账单页的筛选（月份/班级/姓名）已经存在且是传给后端查询的，不用改；只需要在筛选结果上包一层跟学生总览页同款的 `useMemo` 切片逻辑，再渲染 `<Pagination />`。
- **服务端分页**：如果某个机构的学生规模真的涨到让一次性全量拉取变慢（比如要几千人以上），再单独立项把 `GET /api/admin/students` 和 `GET /api/admin/bills` 改成真分页接口（加 `page`/`pageSize` 参数、SQL 层 `LIMIT`/`OFFSET`、返回总数）。本次的纯前端方案不是这个问题的最终解，只是在当前规模下性价比最高的第一步。
