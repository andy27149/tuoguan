# 阶段 1：账号体系与数据隔离 · 设计文档

**对应路线图阶段：** [阶段 1：账号体系与数据隔离](../plans/2026-08-01-托管班系统-项目路线图.md)

**目标：** 打通"机构 → 老师"的登录与权限隔离，产出物为：能用一个老师账号登录、拿到 JWT，且这个 JWT 在跨机构越权访问时被正确拒绝。

## 一、架构选型

沿用阶段 0 已选定的技术栈——不引入 JPA/Hibernate，继续用 `spring-boot-starter-jdbc`（`JdbcTemplate` + 手写 SQL + `RowMapper`）。新增两个依赖：

- `spring-boot-starter-security`：提供 `BCryptPasswordEncoder` 等密码哈希能力，以及 Security Filter Chain 骨架。
- `jjwt`（`io.jsonwebtoken`）：自签发、自校验 HMAC JWT。不接入外部 IdP，不使用 `spring-boot-starter-oauth2-resource-server`——本系统是单体自签 Token 场景，OAuth2 Resource Server 面向的是"校验第三方 IdP 签发的 JWT"场景，引入它需要额外的 JWK/Issuer 配置，对这里没有意义。

**备选方案（不采用）：** 切到 Spring Data JPA 简化 CRUD 代码。不采用的原因：阶段 0 已经明确选择了轻量的 `spring-boot-starter-jdbc` 而非 JPA，中途切换会引入 Hibernate 的复杂度（懒加载、脏检查、N+1 等问题类别）且与已有代码模式不一致，违反 YAGNI。

Spring Security 配置为无状态（`SessionCreationPolicy.STATELESS`）：
- 自定义 `JwtAuthenticationFilter`：解析 `Authorization: Bearer <token>` 请求头，校验签名和过期时间，将 `teacherId`、`institutionId`、`role` 封装进 `Authentication` 的 principal。
- 自定义 `MustChangePasswordFilter`（见第三节）：拦截"必须先改密"的老师访问除改密接口外的其他已认证接口。

## 二、数据模型

新增 Flyway 迁移 `V2__institution_teacher.sql`：

```sql
CREATE TABLE institution (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE teacher (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    institution_id BIGINT NOT NULL,
    phone VARCHAR(20) NOT NULL,
    password_hash VARCHAR(100) NOT NULL,
    role ENUM('ADMIN', 'TEACHER') NOT NULL,
    must_change_password BOOLEAN NOT NULL DEFAULT TRUE,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_teacher_institution FOREIGN KEY (institution_id) REFERENCES institution(id),
    CONSTRAINT uq_teacher_phone UNIQUE (phone)
);
```

设计要点：

- **账号形式为手机号**（`teacher.phone`），**全局唯一**（`uq_teacher_phone`）。登录接口 `POST /api/auth/login` 的请求体只有 `{ phone, password }`，不包含机构信息（PRD 明确不允许老师选择/搜索机构登录，避免暴露机构存在性），因此手机号必须能唯一定位到一条老师记录，不能按机构分别唯一。创建老师账号时若手机号已被占用会报冲突错误，这与常见系统"用户名已存在"提示是同一量级的信息暴露，可以接受。
- `role` 只有 `ADMIN` / `TEACHER` 两种，对应 PRD 中"机构管理员/校长"与"普通老师"，不建单独的 Admin 表——PRD 第五节的数据模型本身就是"老师 Teacher（角色：管理员/普通老师）"这一张表。
- 不在 `teacher` 表冗余存储"所属托管班级列表"——阶段 2 建好 Class 表后，这是通过外键反向查询得到的派生数据，不是 Teacher 自身的字段。
- `V1__baseline.sql` 保持不变（阶段 0 的无操作占位迁移），本阶段迁移从 `V2` 开始。

## 三、登录与 JWT

**登录接口：** `POST /api/auth/login`

请求体：`{ "phone": "13800000000", "password": "..." }`

成功响应：`{ "token": "<jwt>", "mustChangePassword": true }`

失败（手机号不存在，或密码不匹配）：统一返回 `401`，响应体不区分"账号不存在"与"密码错误"，避免泄露账号是否存在的信息。

**JWT 结构：** HMAC-SHA256 签名，密钥从环境变量 `JWT_SECRET` 读取（本地开发在 `.env.example` 中给出示例值，真实 `.env` 不提交）。Claims：

- `sub`：teacherId
- `institutionId`
- `role`：`ADMIN` / `TEACHER`
- `exp`：签发时间 + 30 天

**有效期策略：** 单一长期 Token（30 天），不做 refresh token 机制——过期后重新登录即可。这是内部小工具场景（老师在同一部手机的浏览器上长期保持登录）下便利性优先于安全性的权衡结果；如果未来安全需求提高，可以在不改变对外接口形状的前提下把 30 天缩短或加入 refresh 机制。

**密码存储：** `BCryptPasswordEncoder`，`teacher.password_hash` 只存哈希，不存明文或可逆加密结果。

**首次登录强制改密（后端硬隔离）：**

- `teacher.must_change_password` 默认为 `true`（种子命令创建的账号、以及未来阶段 7 管理员创建的账号都是如此）。
- `must_change_password = true` 时，`JwtAuthenticationFilter` 仍然放行请求（Token 本身有效，用户已认证），但 `MustChangePasswordFilter` 会拦截除 `POST /api/auth/change-password` 之外的所有已认证请求，返回 `403` + `{ "error": "MUST_CHANGE_PASSWORD" }`，前端据此跳转到改密页面。这是后端强制而非仅前端提示——即使前端被绕过（如直接调 API），后端依然拒绝。

**改密接口：** `POST /api/auth/change-password`

请求体：`{ "oldPassword": "...", "newPassword": "..." }`

校验旧密码正确后更新 `password_hash`，并将 `must_change_password` 置为 `false`。管理员创建老师账号（或种子命令）时设置的"初始密码"就是这里的 `oldPassword` 来源。

## 四、数据隔离机制

**核心原则（本阶段建立、后续阶段 2/3 必须延续的约定）：** 任何按机构/老师过滤的资源，`institutionId` / `teacherId` 一律从 JWT（`SecurityContext` 中的 Authentication principal）读取，**绝不接受客户端以参数形式传入**。不会有 `GET /api/institutions/{id}/teachers` 这种把机构 ID 放在 URL 或请求参数里的接口。这样从根源上消除了"篡改 ID 参数即可越权"的攻击面，比"每条 SQL 都记得手动加 `WHERE institution_id = ?`"这种约定式做法更不容易遗漏。Service 层方法统一以从 principal 取得的 `institutionId` 作为隐式上下文参数传给 DAO 层查询方法。

**阶段 1 的验证接口：** `GET /api/teachers/me`

无请求参数，返回当前登录老师自身信息：`{ "id": ..., "phone": "...", "institutionId": ..., "role": "..." }`。

选择这个接口而非直接为 Class/Student 写隔离测试的原因：Class/Student 要到阶段 2/3 才存在，但阶段 1 仍需要一个真实的、端到端的 HTTP 接口来证明"隔离机制在整条链路上确实生效"，而不只是"某个过滤器/切面被调用了"。测试用例：分别用机构 A、机构 B 的老师账号登录拿到各自 JWT；用机构 A 的 JWT 调用 `GET /api/teachers/me`，返回结果中的 `institutionId` 必须是 A，不可能是 B——因为查询逻辑压根不接受外部传入的机构 ID，这个测试验证的是"越权访问在架构上不存在可乘之机"，而不是"某次拦截恰好生效了"。

## 五、临时账号创建入口：种子命令

新增 `SeedCommandLineRunner implements CommandLineRunner`，仅当启动参数包含 `--seed` 时才执行创建逻辑（平时 `docker compose up` 正常启动不会触发这段逻辑）。

参数：`--seed.institution=<机构名> --seed.phone=<手机号> --seed.password=<初始密码>`

用法示例：

```bash
java -jar app.jar --seed --seed.institution="示例机构" --seed.phone="13800000000" --seed.password="Passw0rd!"
```

行为：创建一个新 Institution，及一个隶属于该 Institution、角色为 `ADMIN`、`must_change_password=true` 的 Teacher。若指定手机号已被任意机构的老师占用（`phone` 全局唯一），命令报错退出（不静默覆盖已有数据）。

这个命令不开放任何 HTTP 端点、不常驻运行，符合路线图"建议种子脚本而非未鉴权内部 API，避免留下鉴权隐患"的要求。它是**临时**的：阶段 7 会补齐真正的管理员账号创建 UI/API，届时这个种子命令可以保留作为本地开发/测试的便捷工具，或视情况移除。

## 六、测试策略

沿用阶段 0 已验证的分层测试方式：

- **单元测试（不连真实数据库）：** JWT 签发/校验逻辑（正常签发可解析、过期 Token 被拒绝、篡改签名的 Token 被拒绝）；密码哈希与校验；`MustChangePasswordFilter` 的拦截/放行逻辑。
- **集成测试（需要真实 MySQL）：** 登录成功/失败场景；改密流程（含旧密码校验失败场景）；`GET /api/teachers/me` 的跨机构越权测试（核心验收标准）。集成测试的运行方式（Testcontainers、还是复用 docker-compose 中的 MySQL）由实现阶段的详细计划决定。

## 七、范围界定（本阶段明确不做）

- **管理员创建老师账号的 UI/API**：留待阶段 7。本阶段唯一的账号创建入口是种子命令。
- **忘记密码/管理员重置密码流程**：PRD 未提及具体机制；本阶段改密的唯一路径是老师本人在"首次登录强制改密"场景下通过 `POST /api/auth/change-password` 修改。重置流程留给阶段 7 管理员 UI 一并设计。
- **机构管理员的机构级看板**（PRD 6.11，查看本机构所有老师的班级/学生完成情况）：依赖 Class/Student 数据模型，留待阶段 2/3 之后。

## 八、遗留到后续阶段的决策点

- 阶段 7 设计管理员账号创建 UI 时，需要一并设计忘记密码/重置密码流程。
- 阶段 2/3 引入 Class/Student 后，所有新增的机构隔离资源都必须遵循第四节确立的原则：机构/老师上下文只能来自 JWT，不接受客户端传参。
