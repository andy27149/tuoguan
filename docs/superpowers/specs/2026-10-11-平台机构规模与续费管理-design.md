# 平台机构规模与续费管理 —— 设计文档

## 背景

`PLATFORM_ADMIN` 角色和"平台管理"页面（`PlatformAdminPage`）已经存在，但只做了
两件最小的事：开通新机构（机构名称 + 管理员手机号 + 初始密码）、列出机构名单
（机构名、教师数、创建时间）。完全没有学生数/班级数统计，完全没有"机构服务到
期"这个概念——`institution` 表里没有任何试用期/续费/到期相关字段。

机构端的收费方式此前已经定过方向（2026-09-13 商业化方向讨论）：早期不做自动
订阅扣费，采用"线上扫码 + 人工按周期收款，后台人工标记有效期至某天，到期前人
工提醒续费"。这次要做的，就是把这个一直停留在口头约定层面的"人工
标记 + 人工提醒"，落地成平台管理页里真正可操作的功能：开通机构时设置试用到期
日、到期后能在列表里一眼看出来、续费时能记录一笔历史、到期后能联系上机构。

同时明确一个边界：超级管理员只看各机构的"规模"量级指标（学生数、班级数、教师
数、到期状态），**不看**具体某个孩子/教师的信息，也**不看**机构自己的营收（机
构向家长收的托管费/课时费）——那些是机构自己后台（`AdminOverviewModule` 等）
的事。

家长端"每天扫码查看次数"统计是另一个独立模块（访问日志性质，跟机构生命周期管
理在技术上没有耦合），这次讨论中明确放到下一轮单独设计，不包含在本次范围内。

## 核心设计决策

1. **到期只提醒，不自动锁定**。试用期/订阅到期后，机构的正常登录和使用完全不
   受影响，系统不做任何自动停用。到期状态只在平台管理页的机构列表里用颜色徽
   章高亮出来，由超级管理员自己判断要不要联系机构、要不要真的停用——跟现有
   "人工收款 + 人工跟进"的方向保持一致，不引入自动化强制力。
2. **提醒只做后台列表高亮，不做主动推送**。不接短信/邮件/微信通知，省掉一整
   套外部通知基础设施。超级管理员打开机构列表页时自然看到哪些机构快到期/已
   过期。
3. **到期日是超级管理员直接选的，不是套餐时长自动算出来的**。无论是开通机构
   时设置试用期，还是后续续费，操作方式都是"选一个具体日期"，系统只是把"选
   中的套餐"换算成一个建议日期去预填输入框（比如选"半年"自动填"当前到期
   日+6个月"），但这个日期可以手动改成任意值。这是为了支撑早期"灵活报价/非标
   准优惠期限"的需要，同时避免"提前续费该从哪天开始算"之类的日期运算边界情
   况——不做自动计算，就没有这类边界情况要处理。
4. **试用期和续费是同一套机制，不是两个独立概念**。试用期就是
   `institution_renewal_record` 表里 `plan='TRIAL'` 的一条记录，跟续费记录
   （`plan` 是 `MONTHLY`/`HALF_YEAR`/`YEARLY`）存在同一张表里，走同一个"选套
   餐 + 选日期 + 提交"的操作入口。试用期也不限制只能在开通机构的时候设一次，
   之后要给某个机构追加试用期，同样是再插一条 `plan='TRIAL'` 的记录。
5. **新增机构联系方式字段，独立于登录账号**。`institution` 表新增
   `contact_name`（选填）、`contact_phone`（必填）、`address`（选填）三个字
   段。这三个字段跟机构管理员的登录手机号是两回事——登录手机号是技术凭证，
   不一定是真正负责续费决策的人。这三个字段开通时填，之后也能在列表里编辑，
   不是一次性写死的。
6. **班级数统计先不区分托管班/课外课**。`classCount` 先统计机构下全部教学单元
   （`TeachingUnit`）数量，不拆分 `billingMode=MONTHLY` 的托管班和
   `billingMode=LESSON_COUNT` 的课外课。如果后续发现这个粒度不够用，再单独拆。

## 数据模型

### `institution` 表变更

新增四列：

```sql
ALTER TABLE institution
  ADD COLUMN contact_name VARCHAR(100) NULL,
  ADD COLUMN contact_phone VARCHAR(20) NULL,
  ADD COLUMN address VARCHAR(255) NULL,
  ADD COLUMN valid_until DATE NULL;
```

`valid_until` 为 `NULL` 表示"未设置到期日"（存量老机构迁移后的默认状态，列表
里展示"未设置"而不是误判成"已过期"）。`contact_phone` 在应用层校验必填（开通
机构的接口参数校验），数据库列本身允许 `NULL` 是为了兼容存量数据迁移，不强制
加 `NOT NULL` 约束。

`Institution` 领域记录对应新增四个字段：

```java
public record Institution(Long id, String name, String logoObjectKey, boolean custodyEnabled,
                           boolean offCampusEnabled, String contactName, String contactPhone,
                           String address, LocalDate validUntil, Instant createdAt) {
}
```

### 新表 `institution_renewal_record`

```sql
CREATE TABLE institution_renewal_record (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  institution_id BIGINT NOT NULL,
  plan VARCHAR(20) NOT NULL,              -- TRIAL / MONTHLY / HALF_YEAR / YEARLY
  amount DECIMAL(10,2) NULL,              -- 试用期该字段为 NULL
  valid_until DATE NOT NULL,              -- 这次操作后机构的到期日
  note VARCHAR(255) NULL,
  recorded_by_teacher_id BIGINT NOT NULL, -- 操作的平台管理员
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (institution_id) REFERENCES institution(id),
  FOREIGN KEY (recorded_by_teacher_id) REFERENCES teacher(id)
);
```

每次"开通机构"（写入第一条 `TRIAL` 记录）或"续费"操作，都会：
1. 往这张表插入一条新记录；
2. 把 `institution.valid_until` 同步更新成这条记录的 `valid_until`。

`institution.valid_until` 是当前有效状态的唯一权威字段（列表查询直接读这一列，
不用每次聚合计算），`institution_renewal_record` 是纯历史轨迹，只在查看某个机
构的续费历史时才会查询。

`RenewalPlan` 枚举：

```java
public enum RenewalPlan {
    TRIAL, MONTHLY, HALF_YEAR, YEARLY
}
```

## 状态派生规则

机构列表的"到期状态"不落库，每次查询时用 `valid_until` 和当前日期实时算：

- `valid_until == null` → `NONE`（未设置，灰色）
- `valid_until < today` → `EXPIRED`（已过期，红色，附带过期天数）
- `valid_until - today <= 7` → `EXPIRING_SOON`（即将到期，橙色，附带剩余天数）
- 其余 → `ACTIVE`（有效，绿色）

7 天这个阈值先写死在后端（`PlatformInstitutionService` 里一个常量），不做成机
构可配置项——机构数量还很少，用不上这个灵活度，真有需要再加。

## API 设计（`platform` 模块）

### 开通机构（扩展现有）

`POST /api/platform/institutions`

入参新增：`contactName`（选填）、`contactPhone`（必填）、`address`（选填）、
`trialValidUntil`（必填，`LocalDate`）。

服务层 `createInstitution` 在插入 `institution` 行时一并写入这四个新字段（其
中 `validUntil` 直接等于 `trialValidUntil`），然后插入一条
`institution_renewal_record`（`plan=TRIAL, amount=null,
validUntil=trialValidUntil, note=null, recordedByTeacherId=当前平台管理员`）。

### 机构列表（扩展现有）

`GET /api/platform/institutions`

`PlatformInstitutionSummary` 新增字段：

```java
public record PlatformInstitutionSummary(
        Long id, String name, Instant createdAt, int teacherCount,
        int studentCount, int classCount,
        String contactName, String contactPhone, String address,
        LocalDate validUntil, RenewalPlan currentPlan, InstitutionStatus status) {
}
```

- `studentCount`：`studentDao.findAllByInstitutionId(id)` 过滤 `enrolled=true`
  后计数。
- `classCount`：`teachingUnitDao.findAllByInstitutionId(id).size()`。
- `currentPlan`：该机构最近一条 `institution_renewal_record` 的 `plan`（按
  `created_at` 倒序取第一条；一个机构还没有任何记录——理论上不该发生，因为开
  通机构时必然写一条 TRIAL，但防御性地允许为 `null`）。
- `status`：按上一节的派生规则计算。

实现上跟现有 `listInstitutions()` 一样，对每个机构循环查询（机构数量少，N+1
可接受，不引入批量聚合查询的复杂度）。

### 编辑联系信息（新增）

`PATCH /api/platform/institutions/{id}/contact`

```java
public record UpdateInstitutionContactRequest(String contactName, String contactPhone, String address) {}
```

更新对应三个字段，返回更新后的 `PlatformInstitutionSummary`。

### 续费（新增）

`POST /api/platform/institutions/{id}/renewals`

```java
public record CreateRenewalRequest(RenewalPlan plan, BigDecimal amount, LocalDate validUntil, String note) {}
```

服务层 `recordRenewal`：插入一条 `institution_renewal_record`，然后把
`institution.valid_until` 更新成这次传入的 `validUntil`。返回更新后的
`PlatformInstitutionSummary`。

`amount` 在 `plan=TRIAL` 时允许为 `null`，其余套餐不强制校验必填（延续"早期灵
活报价"的方向，不在后端卡金额）。

### 续费历史（新增）

`GET /api/platform/institutions/{id}/renewals`

返回该机构全部 `institution_renewal_record`，按 `created_at` 倒序：

```java
public record RenewalRecordRow(
        Long id, RenewalPlan plan, BigDecimal amount, LocalDate validUntil,
        String note, String recordedByTeacherName, Instant createdAt) {
}
```

  / 教师数 / 联系人&电话 / 到期状态徽章 / 操作列。
  - 到期状态徽章：`ACTIVE` 绿色"有效至 YYYY-MM-DD"，`EXPIRING_SOON` 橙色"N

  读列表，`fetchRenewalHistory` 拉取），下半部分是新增表单——选套餐（单选：
  试用/月/半年/年）→ 自动预填建议到期日（`max(当前到期日, 今天)` 加上套餐对
  应时长：月 +1 月、半年 +6 月、年 +12 月、试用 +30 天，均可手动改）→ 金额
  输入框预填对应参考价（月 299、半年 1499、年 2899，试用留空且禁用）→ 备注
  选填 → 提交调用 `createRenewal`，成功后刷新机构列表。
- 新增 `EditInstitutionContactModal.tsx`：点「编辑联系信息」打开，三个文本输
  入框，提交调用 `updateInstitutionContact`。

## 范围界定 / 不做

- 不做到期自动锁定登录，只做列表高亮——本次讨论中明确确认的取舍。
- 不做短信/邮件/站内推送通知，只在超级管理员打开机构列表页时展示当下状态。
- 不做机构可配置的"即将到期"提醒天数阈值，先写死 7 天。
- 不做套餐时长自动计算到期日，到期日由超级管理员每次手动选定（套餐只用来预
  填建议值）。
- `classCount` 不拆分托管班/课外课，先给合并总数。
- 不做家长端"每天扫码查看次数"统计——这是独立模块，下一轮单独设计，届时另
  开一份 spec。
- 不改动机构自己的管理后台（`AdminOverviewModule` 等）——联系方式/到期信息
  只在平台管理页（`PLATFORM_ADMIN` 视角）可见可编辑，机构自己的 `ADMIN` 账
  号看不到、也编辑不了这些字段。

  - 新建 migration 后，确认存量机构（`valid_until`/`contact_*` 全为 `NULL`）

  - `PlatformInstitutionService` 新增测试：`createInstitution` 携带新字段后
    机构记录和第一条 `TRIAL` 续费记录都正确写入；`recordRenewal` 覆盖"到期
    前续费"（从当前到期日往后延）和"过期后续费"（这次设计里到期日是手动选
