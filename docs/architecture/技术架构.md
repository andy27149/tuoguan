## 一、技术栈速览

| 层 | 技术 |
|---|---|
| 前端 | React + TypeScript + Vite，Tailwind CSS |
| 前端测试 | Vitest + Testing Library |
| 后端 | Spring Boot 3，原生 JDBC（`JdbcTemplate`，**无 JPA/Hibernate**） |
| 后端鉴权 | Spring Security + JWT（HS256，密钥 ≥32 字节） |
| 数据库 | MySQL 8.0，Flyway 版本化迁移（当前最新 `V27`） |
| 对象存储 | MinIO（学生头像，私有桶 + 限时预签名 URL） |
| 后端测试 | JUnit 5 + Testcontainers（真实 MySQL 容器做集成测试） |
| 部署编排 | Docker Compose（无 Kubernetes），Nginx 反向代理 + certbot 签发 HTTPS |
| CI/CD | **无**——没有 `.github/workflows` 或任何 CI 配置，部署靠 `./deploy.sh` 手动触发 |

**为什么不用 JPA**：全仓库搜不到任何 ORM 依赖，DAO 层手写 SQL（`JdbcXxxDao` 命名模式），这是从阶段 1 就定下的技术选择，不是遗漏。

## 二、代码目录结构

### 后端（`backend/src/main/java/com/tuoguan/backend/`）

按业务域分包，每个包内部通常是 `domain/`（record）+ `dao/`（接口 + `JdbcXxxDao` 实现）+ `service/`（业务逻辑）+ `web/`（Controller + 请求/响应 DTO）四层：

| 包 | 职责 |
|---|---|
| `auth` | 登录、JWT、机构（`Institution`）/教师（`Teacher`）账号体系 |
| `roster` | 学生档案（`Student`）的增删改查 |
| `unit` | 教学单元（`TeachingUnit`，托管班+课外课统一模型）、学生-课外课报名关系 |
| `kanban` | 托管班日常记录：每日任务、每日点评、到校打卡、用餐记录、放学标记 |
| `course` | 课外课消课/充值流水、余额覆盖判定（`CourseAccountService`） |
| `billing` | 月度账单生成、请假记录、班级计费标准 |
| `admin` | 机构管理员视角的聚合接口（跨包读取数据拼成管理后台需要的视图，如账单总览、总览卡片） |
| `platform` | 平台管理员视角：机构开通、续费记录、到期状态 |
| `share` | 家长公开分享页（`PublicShareService`）、分享查看日志 |
| `storage` | MinIO 封装（上传/预签名 URL） |
| `audit` | 轻量操作审计日志（`AuditLogService`），被多个 admin 侧 Controller/Service 注入调用（教学单元变更、学生变更、计费单价变更、账单生成、教师变更），**目前没有查询/展示 UI**，纯粹为未来纠纷排查留痕 |
| `config` | Spring 配置类（`SecurityConfig`/`JwtConfig`/`StorageConfig`/`PasswordEncoderConfig`） |
| `health` | 健康检查接口 |

### 前端（`frontend/src/`）

不使用路由库（无 `react-router`），也不用全局状态库（无 Redux/Zustand）——认证状态是 `AuthContext` 里的一个联合类型状态机（`loading/anonymous/mustChangePassword/authenticated`），页面级切换靠组件内 `useState`。

| 目录 | 内容 |
|---|---|
| `pages/` | 15 个顶层页面，详见 [docs/pages/INDEX.md](../pages/INDEX.md) |
| `components/` | 37 个可复用组件（弹窗、卡片、表单等），按功能命名，不分子目录 |
| `api/` | 21 个文件，每个文件对应一类后端资源（`admin.ts`/`course.ts`/`unit.ts`/`platform.ts`/`publicShare.ts` 等），统一通过 `client.ts` 的 `apiFetch` 发请求并附加 JWT |
| `auth/` | `AuthContext.tsx`，登录态状态机 |
| `kanban/` | 非 UI 的纯工具函数：日期处理（`date.ts`）、卡片颜色计算（`cardStatus.ts`，独立单测）、学校班级分组（`schoolClass.ts`）、科目图标（`subjectIcons.ts`） |
| `hooks/` | 自定义 hook（如 `useToast`） |
| `brand/` | 品牌标识组件 |
| `utils/` | 杂项工具（如 `teacherLabel.ts`） |

## 三、鉴权与多租户隔离

- **JWT**：登录成功后签发，payload 携带 `teacherId`/`institutionId`/`role`，前端存 `localStorage`（key `tuoguan_token`），`apiFetch` 统一附加 `Authorization: Bearer` 头。
- **一条贯穿全系统的安全约定**：所有需要机构隔离的接口，`institutionId`/`teacherId` 一律从 JWT 解析，**不接受客户端传参**——请求体/路径参数里即使带了别的机构 ID 也会被忽略，杜绝"改个参数就能看到别的机构数据"类漏洞。
- **跨机构访问统一返回"不存在"而非"无权限"**：查询时先校验资源的 `institutionId` 是否匹配当前登录者，不匹配时抛 404（`NotFoundException`），不暴露"这个资源其实存在，只是你无权看"的信息。
- **角色**：`Role.ADMIN` / `Role.TEACHER` / `Role.PLATFORM_ADMIN`，用 Spring Security 的 `@PreAuthorize("hasRole('...')")` 标注；管理员账号同时隐式满足教师类接口的鉴权条件（没有专门拦截），这是已知的隐式设计，详见[业务架构 · 二、角色体系](../business/业务架构.md#二角色体系)。
- **首次登录强制改密**：`mustChangePassword` 标记位，前端在这个状态下只渲染改密页面。

## 四、数据库：migration 速查表

当前最新 `V27`，27 个迁移文件均在 `backend/src/main/resources/db/migration/`。按功能分组速览（不是流水账，只挑"这次迁移引入了什么能力"）：

| 范围 | 迁移 | 引入了什么 |
|---|---|---|
| 账号体系 | `V1` baseline、`V2` institution_teacher | 机构/教师表、多租户基础结构 |
| 托管看板 | `V3` task_library_and_roster、`V4` daily_tasks_and_dismissal | 任务模板库、学生名册、每日任务、放学标记 |
| 学生档案 | `V5` student_avatar、`V11` teacher_name | 头像字段、教师姓名字段 |
| 家长触达 | `V6` student_daily_note、`V8` student_share_token、`V9`/`V10` student_pickup_checkin → student_arrival_checkin | 每日点评、分享令牌、到校打卡（命名从"接送"改成"到校"） |
| 平台管理 | `V7` platform_admin | `PLATFORM_ADMIN` 角色基础 |
| 任务库迭代 | `V12` task_template_archive、`V13` task_template_teacher | 模板归档（软删）、模板归属教师 |
| 计费模型演进 | `V14` billing_pricing_leave_and_bills、`V15` flat_tuition_and_paid_flag、`V16` institution_logo、`V17` extra_fee_lesson_pricing | 托管定价从"按天"改"按月固定"（`V15`，破坏性迁移，清空旧配置强制重录）；课外费从"固定月费"改"单价×课时数"（`V17`，同样清空重录） |
| 课外课模型 | `V18` course_catalog_and_consumption、`V19` course_recharge_lesson_units | 课外课程目录、消课记录、充值记录（充值单位统一为课时数） |
| 功能开关 | `V20` institution_feature_flags | `custody_enabled`/`off_campus_enabled`，默认都 `TRUE` |
| **架构统一** | `V21` unify_teaching_unit | **全系统最大的一次结构迁移**：托管班（`class_room`）和课外课程（`course`）合并成统一的 `teaching_unit` 表（`billing_mode` 区分），所有引用表（`student`/`daily_task`/`class_dismissal`/`student_daily_note`/`student_arrival_checkin`/`student_leave_record`/`class_billing_rate`/`monthly_bill`/`student_unit_enrollment`/`course_consumption_record`/`course_recharge_record`）的外键同步改名；课外课原 id 统一加偏移量 `1000000000` 避免和托管班 id 冲突 |
| 审计 | `V22` audit_log | 轻量操作审计日志表（见[二、代码目录结构](#二代码目录结构)的 `audit` 包说明） |
| 托管日常记录 | `V23` student_meal_record、`V24` monthly_bill_leave_line | 用餐记录表、账单里的请假扣减明细行 |
| 平台运营 | `V25` institution_contact_and_valid_until、`V26` institution_renewal_record、`V27` student_share_view_log | 机构联系方式+到期日、续费记录、家长扫码查看日志 |

**读 SQL 时的两个注意点**：
1. `V15`/`V17` 都是"改了计费口径语义但不改列名会被误读成旧语义"的破坏性迁移，处理方式都是**清空旧数据强制管理员重新手动录入**，不是静默迁移——如果以后要加类似的"单价含义变更"，参考这两个迁移的做法。
2. `V21` 的 id 偏移量（课外课 +1000000000）是历史遗留，现在新建的 `teaching_unit` 记录由自增主键统一分配，不会再出现这种偏移，只有 2026-10 之前迁移过来的课外课记录 id 比较大。

## 五、本地开发环境

本机（开发者机器）**只有一套标准 dev/test 环境**，不要为了某次验证额外起新的 docker-compose 栈：

- `tuoguan-local-test-mysql`：MySQL 8.0，host 端口 **23310**，db `tuoguan_local_test`，仅 `root`/`root`
- `tuoguan-local-test-minio`：host 端口 **19000**（API）/ **19001**（控制台），`minio_admin`/`minio_change_me`

**启动后端**（`cd backend`）：
```bash
export DB_PORT=23310
export DB_NAME=tuoguan_local_test
export DB_USERNAME=root
export DB_PASSWORD=root
export JWT_SECRET=change_me_to_a_random_32_byte_or_longer_secret
export MINIO_ENDPOINT=http://localhost:19000
export MINIO_ACCESS_KEY=minio_admin
export MINIO_SECRET_KEY=minio_change_me
mvn spring-boot:run -Dspring-boot.run.jvmArguments="-Dapi.version=1.44"
```
监听 `:8080`。

**启动前端**（`cd frontend`）：`pnpm dev`，监听 `:5173`，`vite.config.ts` 已配置 `/api` 自动代理到 `localhost:8080`。

这套环境和生产环境（见[七、生产部署](#七生产部署)）完全隔离，数据互不影响。

## 六、测试基建

### 前端

`pnpm vitest run`，用 esbuild 转译，**不做类型检查**——这意味着 `vitest` 跑绿不代表 `tsc -b` 也会通过，提交前两个都要跑（曾经真实发生过：`LowBalanceCard.tsx` 缺一个必填 prop，本地测试一直绿灯，直到生产环境 `tsc -b` 构建才报错阻塞部署）。

### 后端：Testcontainers + colima 的已知坑（已解决）

继承 `IntegrationTestBase` 的测试类会用 Testcontainers 启动真实 MySQL 容器做集成测试。如果本机用 **colima** 而非 Docker Desktop 跑 Docker，较新版本的 Docker Engine 和 Testcontainers 默认行为不兼容，表现为"测试挂起或连接被拒绝"，根因是三个独立问题叠加：

1. docker-java 的启动探测硬编码请求 `GET /v1.32/info`，新版 Docker Engine（本机 29.5.2，API 1.54）拒绝低于 1.40 的请求
2. Testcontainers 的清理 sidecar（Ryuk）尝试挂载宿主机 macOS 的 socket 路径到容器内，colima 虚拟机内部没有这个路径
3. 一个独立的代码坑：`@Container` 标注在 `static` 字段上会导致 JUnit5 每个测试类都重启容器，而 Spring 的 `@SpringBootTest` 上下文缓存复用同一个 DataSource（绑定第一个容器的端口），后面的测试类全部连接失败——已修复为手动 `static { MYSQL.start(); }` 的单例容器模式，不再用 `@Container`/`@Testcontainers` 注解

**修复后必须设置的 4 个环境变量**（缺一不可，已写进 `README.md`）：
```bash
export DOCKER_HOST=unix:///Users/<用户名>/.colima/default/docker.sock
export DOCKER_API_VERSION=1.44
export TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock
export JAVA_TOOL_OPTIONS="-Dapi.version=1.44"
```
`DOCKER_API_VERSION` 本身不够——docker-java 实际读取的是 JVM 系统属性 `api.version`，必须通过 `JAVA_TOOL_OPTIONS` 传给 Maven fork 出的测试子进程。Docker Desktop 用户通常不需要这些配置。

### 已知的测试 flaky 模式（不是 bug，是共享容器的副作用）

全套集成测试共享**同一个** MySQL 容器实例，类之间不清库。如果两个不相关的测试文件恰好用了同一个手机号常量，只有在跑**全量测试套件**时才会撞上 `DuplicateKey ... teacher.uq_teacher_phone`，单独跑某个文件看不出来。新增测试用的手机号前先 `grep -rn "<手机号>" backend/src/test --include="*.java"` 确认没人用过，撞上了就换一个未使用的号段。

## 七、生产部署

**完整步骤见仓库根目录的 [`DEPLOY.md`](../../DEPLOY.md)**（313 行，覆盖前置条件、Nginx+certbot 配置、首次部署、日常更新、备份恢复、安全检查清单、常见问题排查），本节只给整体拓扑，不重复 DEPLOY.md 的操作步骤。

### 部署拓扑

Docker Compose 三个文件叠加使用（**本地开发**和**生产**二选一场景，端口映射不能同时声明在两边，否则会端口冲突——这是真实踩过的坑，见 `docker-compose.override.yml` 里的注释）：

| 文件 | 作用 |
|---|---|
| `docker-compose.yml` | 基础服务定义（mysql / minio / backend / frontend），不含端口映射 |
| `docker-compose.override.yml` | 本地开发用的端口映射，`docker compose up`（不显式传 `-f`）会自动叠加 |
| `docker-compose.prod.yml` | 生产用的端口映射（全部绑定 `127.0.0.1`，不直接暴露公网，靠 Nginx 反代），`deploy.sh` 显式用 `-f docker-compose.yml -f docker-compose.prod.yml` 两个文件，不会叠加 override |

### 一键部署脚本

`./deploy.sh`（`--no-pull` 跳过拉代码只重新构建、`--no-cache` 构建不用缓存）：检查 `.env` 存在 → 校验工作区无未提交改动才会 `git pull` → `docker compose build` → `docker compose up -d`。

### 关键环境变量（`.env`，从 `.env.example` 复制）

- `MYSQL_*` / `MINIO_ROOT_*`：数据库和对象存储的凭据
- `MINIO_PUBLIC_ENDPOINT`：**容易踩坑的一项**——后端生成头像等预签名 URL 时必须用浏览器/手机能直接访问到的公网地址，不能用容器内部地址 `http://minio:9000`，需要单独配一个子域名反代到 MinIO（见 DEPLOY.md 第二节）
- `JWT_SECRET`：≥32 字节
- `NPM_REGISTRY`：前端 Docker 构建用的 npm 源，国内服务器建议换镜像源（`registry.npmmirror.com`）避免连 `registry.npmjs.org` 不稳定
- `VITE_BASE_PATH`：只有部署在非根路径子目录时才需要改，构建时打包进静态资源，改了必须 `--no-cache` 重新构建才生效

### 没有 CI/CD

仓库里没有任何 CI 配置文件，没有自动化测试门禁、没有自动部署流水线。合并到 `main` 和实际部署是两个完全独立、都需要人工触发的动作——`deploy.sh` 会在 `git pull` 之后用那一刻的 `main` 分支内容构建，但**谁来决定什么时候跑 `deploy.sh`、pull 下来的代码有没有先跑过测试，完全靠人**。
