# 奕成长课后平台 · 代码架构（叙事性说明）

> **文档定位**：讲"稳定不常变"的分层约定和跨模块依赖方向——不逐类枚举，具体某个类/函数做什么，直接用 `search_graph`/`get_code_snippet`/`trace_path` 查代码图谱（已索引，见 [docs/INDEX.md](../INDEX.md) 的"技术架构"一节），比写一份随时会过时的静态类清单更可靠。这篇文档的价值在于回答"新功能该放哪个包""跨模块调用该走哪个方向"这类设计判断，不是回答"这个方法叫什么名字"。
>
> **最后核实时间**：2026-10-12，部分数据来自代码图谱的聚类/调用链分析（4212 节点/15078 边）。

## 后端分层约定

每个业务域包（`auth`/`roster`/`unit`/`kanban`/`course`/`billing`/`admin`/`platform`/`share`）内部统一是四层结构，各层文件名也有固定模式：

```
<domain>/
 ├─ domain/   纯数据的 Java record，无行为方法（如 Student、TeachingUnit）
 ├─ dao/      接口 + JdbcXxxDao 实现，直接写 SQL（JdbcTemplate），不经过任何 ORM
 ├─ service/  业务逻辑、跨 DAO 编排、权限校验（requireXxxInInstitution 这类方法）
 └─ web/      Controller + 请求/响应 DTO（record），只做参数校验和 service 调用，不写业务逻辑
```

**为什么 DAO 是接口+实现分两个文件**：历史上是为了方便测试替身，但实际上全仓库测试都是 Testcontainers 真实数据库集成测试（见[技术架构 · 六](./技术架构.md#六测试基建)），没有真的用过 mock 实现——这个分层目前更多是命名约定的惯性，不是因为真的需要多套实现。

## 跨业务域调用：谁依赖谁

业务域之间不是完全对等的，有明确的依赖方向（用代码图谱的调用链验证过，不是臆测）：

```
admin / platform（聚合/管理视角）
        │ 依赖
        ▼
billing ──依赖──▶ course（月度账单生成时要问 course 域"这个月哪些消课没被充值覆盖"）
   │
   ├─ 依赖 unit（教学单元信息：是托管班还是课外课、计费标准）
   ├─ 依赖 roster（学生信息）
   └─ 依赖 kanban（用餐记录，算餐费）

share（家长公开页）──依赖──▶ kanban（月度统计）+ course（课外课情况/对账单）

kanban / course / unit / roster（基础业务域）
        │
        ▼
   互相之间只在必要时单向依赖（如 unit 被几乎所有域引用，因为"教学单元"是核心枢纽实体）
```

**具体验证过的例子**：`BillGenerationService.generateBill`（`billing`）调用链里直接出现 `CourseAccountService.classifyConsumptions`（`course`）——这正是[业务架构 · 五、课外课计费与结算](../business/业务架构.md#五课外课计费与结算充值覆盖--月度账单兜底)里"账单生成时读取课外课覆盖判定结果"这条业务规则在代码里的落地。同一条调用链里还会看到 `AuditLogService.record`（`audit`）——生成账单这个动作会被记入审计日志。

**反过来不成立**：`course`/`kanban`/`unit`/`roster` 这些基础业务域不会反过来调用 `billing`/`admin`/`platform`——后者是"聚合/编排"层，前者是"数据与规则"层。新加功能时，如果发现要在基础业务域里调用 admin 包的东西，这通常是个信号：说明这段逻辑放错域了，应该挪到 admin 包，或者拆出一个新的更底层的共享方法。

## `admin` 包的特殊性：它是聚合层，不是独立业务域

`admin` 包里的 Controller（如 `AdminBillOverviewController`、`AdminStudentController`）本身不定义新的核心领域概念，而是读取/编排其他域的数据，拼成管理后台需要的视图（账单总览、总览卡片等）。这是故意的设计——机构管理员的大部分操作本质是"跨域查看+少量写操作"，没必要在每个基础域里都加一套"管理员视角"的方法。

## 前端：薄 API 层 + 无状态管理库

```
pages/        15 个页面组件，大部分页面自己管理所有 useState，不共享状态
components/   37 个可复用展示/弹窗组件，通过 props 接收数据和回调，不直接发请求
  （例外：少数弹窗组件内部自己调 api/，比如 AdminCourseStatementModal 自己管理充值表单状态）
api/          21 个文件，每个文件对应后端一类资源，是前端唯一允许出现 fetch/apiFetch 调用的地方
auth/         AuthContext，唯一的全局状态（登录态），其余状态都是组件局部的
```

**没有全局状态库、没有路由库是故意的**：15 个页面之间的切换都是"父组件 useState 一个 view 变量 + 条件渲染"（见 `App.tsx`/`AdminDashboardPage.tsx`），数据流是单向的 props 传递，没有引入 Redux/Zustand/React Router 这类依赖。这在当前规模下是合理的——不要在不了解这个决策背景的情况下"顺手"引入状态管理库或路由库，那会违反现有约定，让一部分页面用新模式、一部分用旧模式，增加理解成本。

**api/\*.ts 是前后端的唯一边界**：组件永远不直接拼 URL 或处理 `fetch`，统一经过 `api/client.ts` 的 `apiFetch`（自动附加 JWT、统一错误处理成 `ApiError`）。改接口时，前端只需要改对应的 `api/*.ts` 文件和调用它的组件，不会有组件绕过这一层直接发请求。

## 测试基建的架构影响

后端集成测试全部继承 `IntegrationTestBase`，共享同一个 MySQL 容器实例贯穿整个测试套件运行（单例容器模式，不是每个测试类独立启停）。这个决定的代码后果：
- 测试之间**不清库**，新增测试要自己保证数据隔离（比如用唯一的机构名/手机号，不依赖"数据库是空的"这个假设）
- 跨测试文件的硬编码常量（尤其是手机号）有全局唯一性要求，这是[技术架构 · 六](./技术架构.md#六测试基建)里提到的已知 flaky 模式的根源
