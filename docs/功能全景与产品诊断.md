### #01 · 高风险 — 课外课消课完全不校验余额 ✅ 已修复（2026-10-03）
**现象**：系统有「充值」和「消课」概念，但消课时从不检查余额，哪怕余额为负也能继续，唯一反馈是对账单上的负数。
**影响**：点名默认全勾，容易在未提醒续费时持续产生「欠课时」，只能靠人工翻账单发现。
**代码**（2026-10-12 校正行号）：`course/service/CourseConsumptionService.java:101` `recordBatchConsumption`（仍然无余额检查，确认行为没有变化）；`CourseAccountService.java:76` `getStatement`（余额仅用于展示）。
**已做**：`listRosterForCourse` 新增按课程计算的 `balance`，`CourseConsumptionPage.tsx` 点名列表里余额 ≤0 标红提示，不阻断消课（按用户决策，暂不做阻断开关）。

### #02 · 高风险 — 同一动作，三套互不相通的财务处理 ✅ 已修复（架构统一，按本诊断当初的中长期建议实现）
**现象（历史）**：「确认上了一节课外课」的财务处理曾经完全取决于该生是否同时在托管班：无托管班→预充值/余额模式，无正式账单；有托管班→不允许预充值（`recharge` 对有班级的学生抛 `RechargeNotAllowedException`），费用月底自动追加进托管账单附加费。
**影响（历史）**：财务人员要理解两套规则，同类学生收费体验不一致，容易引发核账混乱和家长困惑。
**已做（完整架构统一，不只是短期缓解）**：`RechargeNotAllowedException` 已从代码中完全移除——**现在任何报了课外课的学生都可以充值，不再区分是否同时在托管班**。消课是否计费统一由 `CourseAccountService.classifyConsumptions`/`classifyForCourse` 按"学生+课程"把充值和消课事件按时间顺序回放判定：充值余额覆盖的消课不收费，未覆盖的部分在 `BillGenerationService.generateBill` 生成月度账单时自动计入"课外课附加费"一行——**这套结算规则现在对所有学生统一适用**，`BillGenerationService.computeCourseConsumptionRows` 头部注释明确写着"覆盖判定的唯一权威来源是 CourseAccountService.classifyConsumptions——它对任何学生都适用"。连带效果：纯课外课学生现在也会生成正式的月度账单（学费/餐费记 0，只汇总未覆盖的课外课费用），不再是"无正式账单"。
**遗留的不一致**：家长分享页对双重身份学生仍只展示轻量的"当日课外课情况"（不展示充值/余额），`PublicShareService`/`CourseAccountService.getCourseActivity` 处的代码注释仍写着"这类学生从不预充值，余额概念不成立"——这句注释已经和当前的充值规则不一致，是代码注释没有跟上架构统一的遗留问题，不代表产品决策，建议找时间订正注释并评估是否要把余额信息也展示给这类学生的家长看。
**代码**：`CourseAccountService.java` `recharge`（已无身份限制）/`classifyConsumptions`/`classifyForCourse`；`BillGenerationService.java` `computeCourseConsumptionRows`/`generateBill`/`generateBillsForInstitution`（遍历全机构所有在读学生，不分身份）。

### #03 · 高风险 — 纯课外课学生在「账单管理」完全不可见 ✅ 已修复（教学单元合并时顺带解决）
**现象**：账单管理严格按托管班组织，纯课外课学生没有班级，结构性地不会出现。唯一入口是「学生总览」操作列的按钮。
**影响**：月度财务核对时容易完全遗漏这部分学生的欠费风险，尤其叠加 #01 后更隐蔽。
**建议**：在账单管理页顶部增加「纯课外课学生」分区，至少汇总展示余额异常学生。
**代码**：`AdminBillingModule.tsx`（按班级分组）；`AdminStudentsModule.tsx`（按钮仅对 `offCampusOnly` 展示）。
**已做**：托管班+课外课合并为统一教学单元模型后，`BillGenerationService.generateBill` 不再因缺少班级 404，`getBillOverview`/`getBillOverviewAllMonths` 改为遍历全部学生，纯课外课学生自然出现（学费/餐费记 0，只汇总课外课消课附加费）。

### #05 · 中 — 班级 vs 课程：两个相似实体，治理方式完全相反 ✅ 已修复（教学单元合并时解决）
**现象**：托管班级只能教师自建，管理员不能新建；课外课程只能管理员建且必须指定教师，教师无自建入口。
**影响**：两个业务上相似的「教学单元」权限模型完全反转，增加培训/理解成本。
**建议**：若有刻意的业务考虑应显性说明；若无特殊考虑，可让管理员也能建班级。
**代码**：`AdminClassRoomController.java`（仅 GET/PATCH/DELETE，无 POST）；`AdminCourseController.java:34`（POST，教师 id 必填）。
**已做**：托管班+课外课合并为统一 `AdminTeachingUnitController`，建班/建课/改派/启停/删除统一收归管理员（`@PreAuthorize("hasRole('ADMIN')")`），教师自建班级/学生入口（`POST /api/classes`、`POST /api/classes/{id}/students`、课外课自建+报名）已硬下线。

### #06 · 中 — 家长分享链接：托管统计与课外课账单互斥展示 ✅ 已修复
**现象（历史）**：分享页只按「是否有托管班」二选一，双重身份学生的家长看不到课外课情况。
**已做**：`PublicShareService.getShare` 现在按本诊断当初的建议改为"有则都展示"——`teachingUnitId != null` 分支会同时返回月度托管统计（`stats`）和课外课情况（`courseActivity`，若该生报了课外课），不再互斥；courseActivity 还在后续迭代中从"最近5条全量记录"改成了按当前查看月份过滤、跟随家长选中的日历日期动态展示当天实际上的课。
**代码**：`PublicShareService.java` `getShare`。

### #07 · 中 — 机构功能开关只是「前端软开关」⚠️ 部分缓解（仅创建环节，非全面拦截，待与用户确认是否算已解决）
**现象**：关闭托管/课外课只隐藏导航入口，底层接口无机构级拦截，理论上仍可被直接调用成功。
**2026-10-12 核实发现**：`AdminTeachingUnitService.create` 现在会在**创建**教学单元时校验对应功能开关（`!institution.custodyEnabled()` / `!institution.offCampusEnabled()` 时抛 `FeatureDisabledException`），这是本次核实时新发现的、诊断文档此前没有记录的校验。但这只拦住"新建"这一个动作——对**已存在**的班级/课程继续打卡、布置任务、点名消课等日常操作，后端仍然没有按机构功能开关做拦截（即关闭托管后，已有托管班的日常看板操作接口不受影响）。核心问题"关闭开关不能让已有功能停止工作"仍然成立，不建议标记为完全修复。
**建议**：暂不改造，但在内部文档标注「开关目前只在创建新单元时生效，不影响已有数据的日常操作」；接入对外 API 时再补全面的后端校验。
**代码**：`AdminInstitutionService.java` `updateFeatureFlags`（仅校验不能同时为 false）；`AdminTeachingUnitService.java` `create`（新发现的创建时校验）；`AdminSidebar.tsx` `isModuleHidden`（纯前端判断）。

### #08 · 低（设计权衡） — 点名消课没有「缺席」记录，历史不可追溯
**现象**：未勾选学生不生成任何记录，呼应「课外课无请假概念」的简化设计。
**影响**：事后无法区分「教师忘记点名」和「学生确实没来」，费用争议时缺乏依据。
**建议**：暂不建议改动核心逻辑；如投诉增多可加一条轻量操作日志（「本日已点名，共到 N 人」），不改变语义。
**代码**（2026-10-12 校正行号）：`CourseConsumptionService.java:101` `recordBatchConsumption`。

### #09 · 低（已验证实现正确） — 管理员的「教师身份」是隐式的
**现象**：管理员的只读看板正确路由到受限只读接口（`adminKanbanApi`，仅 GET，UI 带「只读」徽标，修改按钮全部隐藏）；但管理员同时满足所有未标注 `@PreAuthorize` 的教师接口鉴权条件，理论上可通过其他路径以教师身份操作任意本机构班级。
**影响**：当前 UI 路径设计正确、无实际漏洞，但权限模型依赖「前端不提供入口」而非「后端禁止」，属隐式约定。
**建议**：无需改动，建议在接口文档中备注这一边界，避免未来新增接口产生错误权限假设。
**代码**（2026-10-12 校正行号）：`KanbanPage.tsx:56`（`isAdmin` 判定）及其后多处分支调用 `adminKanbanApi.*`；`AdminKanbanController.java`（class 级 `@PreAuthorize("hasRole('ADMIN')")`，仅 GET）。
