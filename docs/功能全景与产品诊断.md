### #01 · 高风险 — 课外课消课完全不校验余额 ✅ 已修复（2026-10-03）
**现象**：系统有「充值」和「消课」概念，但消课时从不检查余额，哪怕余额为负也能继续，唯一反馈是对账单上的负数。
**影响**：点名默认全勾，容易在未提醒续费时持续产生「欠课时」，只能靠人工翻账单发现。
**代码**（2026-10-12 校正行号）：`course/service/CourseConsumptionService.java:101` `recordBatchConsumption`（仍然无余额检查，确认行为没有变化）；`CourseAccountService.java:76` `getStatement`（余额仅用于展示）。
**已做**：`listRosterForCourse` 新增按课程计算的 `balance`，`CourseConsumptionPage.tsx` 点名列表里余额 ≤0 标红提示，不阻断消课（按用户决策，暂不做阻断开关）。

### #02 · 高风险 — 同一动作，三套互不相通的财务处理 ✅ 已修复（架构统一，按本诊断当初的中长期建议实现）
**现象（历史）**：「确认上了一节课外课」的财务处理曾经完全取决于该生是否同时在托管班：无托管班→预充值/余额模式，无正式账单；有托管班→不允许预充值（`recharge` 对有班级的学生抛 `RechargeNotAllowedException`），费用月底自动追加进托管账单附加费。
**影响（历史）**：财务人员要理解两套规则，同类学生收费体验不一致，容易引发核账混乱和家长困惑。
**已做（完整架构统一，不只是短期缓解）**：`RechargeNotAllowedException` 已从代码中完全移除——**现在任何报了课外课的学生都可以充值，不再区分是否同时在托管班**。消课是否计费统一由 `CourseAccountService.classifyConsumptions`/`classifyForCourse` 按"学生+课程"把充值和消课事件按时间顺序回放判定：充值余额覆盖的消课不收费，未覆盖的部分在 `BillGenerationService.generateBill` 生成月度账单时自动计入"课外课附加费"一行——**这套结算规则现在对所有学生统一适用**，`BillGenerationService.computeCourseConsumptionRows` 头部注释明确写着"覆盖判定的唯一权威来源是 CourseAccountService.classifyConsumptions——它对任何学生都适用"。连带效果：纯课外课学生现在也会生成正式的月度账单（学费/餐费记 0，只汇总未覆盖的课外课费用），不再是"无正式账单"。
**遗留的不一致**：家长分享页对双重身份学生仍只展示轻量的"当日课外课情况"（不展示充值/余额），`PublicShareService`/`CourseAccountService.getCourseActivity` 处的代码注释仍写着"这类学生从不预充值，余额概念不成立"——这句注释已经和当前的充值规则不一致，是代码注释没有跟上架构统一的遗留问题，不代表产品决策，建议找时间订正注释并评估是否要把余额信息也展示给这类学生的家长看。
**代码**：`CourseAccountService.java` `recharge`（已无身份限制）/`classifyConsumptions`/`classifyForCourse`；`BillGenerationService.java` `computeCourseConsumptionRows`/`generateBill`/`generateBillsForInstitution`（遍历全机构所有在读学生，不分身份）。

**建议**：暂不改造，但在内部文档标注「开关目前只在创建新单元时生效，不影响已有数据的日常操作」；接入对外 API 时再补全面的后端校验。
**代码**：`AdminInstitutionService.java` `updateFeatureFlags`（仅校验不能同时为 false）；`AdminTeachingUnitService.java` `create`（新发现的创建时校验）；`AdminSidebar.tsx` `isModuleHidden`（纯前端判断）。

## 第二轮诊断（2026-10-13）· 一、业务与产品缺口

> 来源：资深教辅机构从业人员 + 资深产品经理两份独立审查，重合发现已合并。

### #10 · 高 — 增长飞轮的核心动作"引导关注公众号"在产品里没有任何实际触点
**现象**：商业模式明确写着家长端靠"关注公众号"转化，但分享页、分享海报全文搜索"公众号"/二维码零命中；家长扫码只会看到孩子的学习报告或课外课对账单，看完就关掉。纯课外课学生查看对账单（家长关注度最高的时刻之一）同样没有任何关注引导。
**影响**：`StudentShareViewLog` 统计的"查看次数"和商业化真正要的"涨公众号粉丝"是两件事，增长目标无法被产品验证或推动，整套增长策略停留在文档层面。
**建议**：在分享页/海报、尤其是课外课对账单页加一个真实可配置的公众号关注引导位（二维码+文案）。
**代码**：`ParentSharePage.tsx`、`SharePosterModal`/`ShareLinkModal`。

### #11 · 高 — 账单欠费提醒夹杂大量 ¥0.00 空账单，稀释真实欠费信号 ✅ 已修复（2026-10-13）
**现象**：纯课外课学生当月消课全被充值覆盖时仍会生成一条 ¥0.00 的账单且状态为"未缴费"；机构总览"账单欠费提醒"卡片按生成顺序平铺全部未缴费记录，无金额过滤/排序/高度上限。实测环境 42 笔欠费里近一半是 ¥0.00，且和真实大额欠费共用同一个橙色"●未缴费"徽标。
**影响**：真正该催收的对象被淹没在无意义的 0 元提醒里，前台要逐条点开才能分清，随数据积累只会越来越严重。
**已做**：`BillGenerationService.getUnpaidBillSummary` 过滤条件新增 `totalAmount > 0`，¥0.00 账单不再计入"未缴费"统计（账单本身仍正常落库，`AdminBillingModule` 逐条列表不受影响，零元账单继续原样展示）；`UnpaidBillsCard.tsx` 对拿到的行按金额降序排序，并加滚动高度上限避免卡片被撑爆。补充了后端单元测试验证零元/非零账单的过滤行为。
**代码**：`BillGenerationService.java` `getUnpaidBillSummary`；`UnpaidBillsCard.tsx`。

### #12 · 高 — 全链路没有任何主动触达能力，平台到机构、机构到家长都靠人工肉眼+微信喊话
**现象**：系统没有短信/模板消息/企业微信机器人等任何外发通知渠道。机构到期/欠费提醒只在平台管理员列表/机构总览页肉眼可见；账单生成后家长收不到任何提醒，全靠教师在微信群手动喊话。
**影响**：续费流失和收款逾期无法被动发现，收款周期被教师个人勤勉度左右，机构数变多后平台管理员会漏看，直接影响订阅收入和现金流。
**建议**：至少给"到期前 N 天""欠费超过阈值"两类场景接一条自动短信/企业微信机器人通知；评估账单生成/超期是否也能通知家长。

### #13 · 高 — 学生停用/离校没有退费与余额清算流程
**现象**：停用学生只是把 `enrolled` 置为 false，不检查未缴账单、不检查课外课充值余额，全系统没有"退费"概念。
**真实场景**：学生转学时还剩若干课外课课时没上完，或多收了半个月餐费，家长要求退钱，机构只能线下用现金/转账解决，系统账目和实际资金流脱节。
**建议**：停用学生时提示未结清账单和课外课余额，补一个退费登记入口（哪怕只是备注金额，不做真实退款对接）。
**代码**：`AdminStudentsModule.tsx` `handleConfirmDeactivate`；`AdminStudentController` 停用接口。

### #14 · 高 — 账单催收能力薄弱：无逾期排序/批量操作，收款不记录方式也不支持部分收款 ⚠️ 部分修复（2026-10-13，按用户决策缩小范围）
**现象**：账单管理页 42 笔欠费按生成顺序平铺，没有逾期天数排序、批量操作、导出；"是否已缴费"只是一个布尔开关，没有现金/微信/支付宝/银行转账的区分字段，也不能登记部分收款。
**真实场景**：家长先转一半学费说"过两天补齐"，前台要么硬标"未缴费"忘记已收部分，要么标"已缴费"但实际没收全；月末对账时无法核对各渠道流水分别收了多少，现金环节尤其容易出现经手人昧款难发现的风险。
**范围确认（已与用户确认）**：本次只做 UI 层面的排序/逾期展示 + 收款方式字段，不做部分收款登记（即不做金额拆分/多次收款记录），这部分仍是遗留缺口。
**已做**：`monthly_bill` 新增 `payment_method` 字段（现金/微信/支付宝/银行转账），标记已缴费时必须选择收款方式；`BillOverviewRow`/`UnpaidBillRow` 新增 `overdueDays`（约定到期日=账单所属月份月底）；`AdminBillingModule.tsx` 加逾期天数列和排序（默认/逾期优先/金额优先）。后端批量标记接口（`PATCH /admin/bills/batch-paid`）已实现并保留。
**后续发现的 UX 问题及处理**：批量标记上线后，用户发现页面同时存在"批量标记已缴费"和"一键生成本月账单"两个入口，但学生勾选框（checkbox）只对前者生效、对后者无效，容易造成误解。讨论后决定**暂时从前端移除批量标记已缴费功能和对应的 checkbox**（后端接口保留不删），等真实使用一段时间、有明确业务反馈后再重新评估是否需要、以及如何统一交互。
**代码**：`AdminBillingModule.tsx`、`billing/domain/PaymentMethod.java`、`MonthlyBillDao`/`JdbcMonthlyBillDao`（`setPaid` 签名加收款方式）、`BillGenerationService.java`（`overdueDaysFor`/批量标记方法保留）。

### #15 · 中 — 平台方没有机构"健康度"指标，到期日是滞后的流失信号

## 第二轮诊断（2026-10-13）· 二、技术架构与可扩展性

> 来源：资深架构师审查，全程用代码知识图谱（`transitive_loop_depth`/`linear_scan_in_loop` 等指标）定位真实热点，并核对了全部 Flyway migration 的索引情况，证据均为 file:line 或 qualified_name，非主观猜测。**#33 是一个现在就成立的真实代码缺陷，建议优先单独修复**，其余按"多大体量会成为问题"的紧迫度排列。

### #33 · 高（现在就成立的代码缺陷） — 批量生成账单时 `@Transactional` 被自调用绕过，循环内写操作失去事务保护 ✅ 已修复（2026-10-13）
**现象**：`generateBill`（`BillGenerationService.java:201-202`）标了 `@Transactional`，但批量入口 `generateBillsForInstitution` 在**同一个类内部直接调用** `generateBill(...)`，Spring AOP 代理拦截不到类内自调用，事务注解实际不生效。
**影响**：`monthly_bill` upsert 成功但明细表（附加费/用餐/请假行）插入失败时不会回滚，账单金额和明细行可能对不上；不依赖数据量，现在就成立。
**已做**：给 `BillGenerationService` 注入一个指向自己的 `@Lazy` 代理（`self`），`generateBillsForClass`/`generateBillsForInstitution`/3 参重载的 `generateBill` 一律改成调用 `self.generateBill(...)` 而不是 `this.generateBill(...)`，让每次调用都重新经过代理，`@Transactional` 真正生效。新增 `BillGenerationTransactionalityTest`：用 `@SpyBean` 强制 `MonthlyBillMealLineDao.insert` 在批量生成中途抛异常，验证修复前账单主表会残留（RED），修复后整笔回滚（GREEN）。
**代码**：`BillGenerationService.java`（新增 `self` 字段+构造参数，`generateBill`/`generateBillsForClass`/`generateBillsForInstitution` 调用点）；`billing/service/BillGenerationTransactionalityTest.java`。

### #34 · 高 — "一键生成账单"同步跑全机构学生，且每个学生都做全历史回放
**现象**：`generateBillsForInstitution`（`transitive_loop_depth=4`）在一次 HTTP 请求内对筛选出的全部学生逐个调用 `generateBill`→`computeCourseConsumptionRows`→`CourseAccountService.classifyConsumptions`，后者对该学生**全部历史**充值+消课记录各做一次全表查询再在内存回放排序。
**会在什么体量下出问题**：单机构学生数破千、或机构运营年限变长导致单生历史记录数变多时，一次点击所需的 DB 往返次数和单次回放耗时同时增长，容易超过 Nginx/浏览器超时。
**建议**：改成异步任务+进度轮询；给 `classifyConsumptions` 引入按月的余额快照，避免每次都从头回放全部历史。

### #35 · 高 — 账单总览/总览所有月份接口对全机构学生做 N+1 查询，且无分页
**现象**：`getBillOverview`/`getBillOverviewAllMonths`（均 `transitive_loop_depth=4`）按教学单元遍历，内部对每个学生单独查 `monthlyBillDao.findAllByStudentId`；`StudentOverviewOrder.computeFirstCourseNames` 还对每个纯课外课学生单独查 `enrollmentDao.findAllByStudentId`。
**会在什么体量下出问题**：单机构学生数破千时，账单管理/学生总览每次打开就是成百上千次独立 DB 往返，返回列表本身也无分页。
**建议**：用 `IN` 批量查询替代逐条查询，总览列表加分页。

### #36 · 高 — 管理后台"今日概览"对每个托管班做 4 次独立查询
**现象**：`AdminStatsService.getTodaySnapshot`（`linear_scan_in_loop=1`）for 循环遍历机构全部托管班，每个班单独查到校/用餐/请假/任务 4 张表，无批量查询。
**会在什么体量下出问题**：单机构班级数从十几涨到上百时，打开一次首页就要 400+ 次 DB round trip；这是管理员登录后最先看到、刷新最频繁的页面。
**建议**：按 `institutionId` 一次性批量查当天记录，内存按 unit 分组聚合。

### #37 · 中高 — "低结余预警"对全机构历史记录做嵌套扫描，接近 O(n²)
**现象**：`CourseAccountService.getLowBalanceEntries` 先取出全部历史充值+消课记录，再对每个"学生+课程"组合重新扫一遍这两个全量列表算余额。
**会在什么体量下出问题**：机构历史充值/消课记录从几百条涨到几万条后，嵌套扫描的耗时呈平方级增长，且每次请求都重算、无缓存。
**建议**：一次 `groupingBy` 分组统计代替逐 key 重新过滤；长期应下推到 SQL 层 `GROUP BY`。
**代码**：`CourseAccountService.java:113-150`。

### #38 · 中 — 无缓存层，多机构共享单一 MySQL 实例，没有隔离
**现象**：技术栈无 Redis；总览类接口（今日概览/低结余/欠费统计/营收快照）每次请求都直接命中 MySQL 做全量聚合，所有机构靠 `institution_id` 过滤共享同一套表、同一实例。
**会在什么体量下出问题**：机构数破百、且出现一两个数据量明显更大的机构时，大机构的慢查询会占用数据库资源，拖慢同实例上其它小机构的请求（噪声邻居效应）。
**建议**：给总览类接口加短 TTL 缓存（哪怕先用进程内 Caffeine），为后续接入 Redis 留好接口边界。

### #39 · 中 — 单体单实例部署，水平扩展路径不清晰，连接池未显式调优
**现象**：`docker-compose.yml`/`docker-compose.prod.yml` 只定义一个 `backend` 容器，无多副本配置；`application.yml` 未显式配置 HikariCP 参数（默认 `maximum-pool-size=10`），而 #34-#37 的热点单次请求可能连续占用连接执行几十到上百次串行查询，容易把默认连接池耗尽。
**会在什么体量下出问题**：并发在线人数/QPS 触及单机 CPU、内存或默认连接池上限时，通常对应机构数上百、同时在线上千；容器重启期间也是单点故障，整个平台不可用。
**建议**：提前验证"Nginx 反代多个 backend 副本"的可行性，并结合压测结果显式配置 HikariCP 连接数上限（副本数 × 单实例连接数不超过 MySQL `max_connections`）。

### #40 · 中 — JWT 30 天长有效期，无撤销/黑名单机制

### #43 · 低 — MinIO 单实例、单 volume，无副本/生命周期策略
**现象**：MinIO 是单容器 `server /data`，没有 distributed mode，也没有对象生命周期规则，所有头像类小文件堆在一个 volume 里。
**影响**：当前体量下存储空间本身不是瓶颈，真正的风险是单点故障——这台机器磁盘损坏会丢失全部机构的头像文件。

### #75 · 高 — 课外课点名消课存在查后插竞态，并发/重复提交会导致家长被多扣课时费
**现象**：`CourseConsumptionService.recordBatchConsumption` 判断"这条消课记录是否已存在"和"插入新记录"是两个独立步骤（先查 `findAllByStudentIdAndTeachingUnitIdAndDate(...).isEmpty()`，为空才插入），中间没有任何数据库层面的互斥；`course_consumption_record` 表也没有 `(student_id, course_id, consumption_date)` 唯一约束兜底（建表迁移脚本的注释原文写的是"故意不加日期唯一约束，由服务层负责重复提醒与二次确认"，但服务层这个"负责"目前是有竞态漏洞的）。
**复现方式**：两个线程同时对同一学生、同一门课、同一天调用 `recordBatchConsumption`，稳定复现（3/3 次独立验证）为该学生当天生成两条消课记录而不是一条。
**真实场景**：老师点"确认消课"时网络卡顿手滑连点两下，或者客户端网络重试导致同一次点名被发送了两次请求，几乎同时到达服务端。
**影响**：家长会被多扣一次课时费，属于真金白银的计费错误，且目前没有任何机制能自动发现这种重复（家长自己翻账单核对消课记录可能会发现，但这是被动依赖用户投诉）。
**建议**：给 `course_consumption_record` 表加 `(student_id, course_id, consumption_date)` 唯一约束从根上堵住，或者在应用层用单机内存锁把"查+插"这段逻辑串行化（当前单机单实例架构下足够）；加约束前需要先排查生产数据里是否已经存在重复记录。
**代码**：`course/service/CourseConsumptionService.java` `recordBatchConsumption`；`backend/src/main/resources/db/migration/V18__course_catalog_and_consumption.sql`（`course_consumption_record` 建表）；回归测试已写好但禁用：`course/service/CourseConsumptionConcurrencyTest.java` `concurrentDoubleSubmissionOfSameRollCallDoesNotCreateDuplicateConsumptionRecords`。

### #76 · 中 — 并发生成同一学生同月账单时，`upsert` 内部的查回偶发找不到刚写入的行
**现象**：`monthly_bill` 表有 `(student_id, bill_month)` 唯一约束，`JdbcMonthlyBillDao.upsert` 用的是 `INSERT ... ON DUPLICATE KEY UPDATE` 原子语句（而不是查后插），本来预期这条路径天然对并发安全。但实测：两个线程并发对同一学生同一月份调用 `BillGenerationService.generateBill` 时，`upsert()` 内部紧跟在 INSERT 语句之后、同一个事务里按 `(student_id, bill_month)` 查回这一行的那次 `SELECT`，会抛 `IllegalStateException: Bill not found after upsert`——INSERT 本身没有报任何 SQL 异常。
**复现方式**：3/3 次独立验证稳定复现，已排除 `self` 代理自调用绕过 `@Transactional`（见 #33）、测试本身误用等常见假象原因。
**根因**：尚未完全定位到 InnoDB 层面的确切机制——按正常理解，同一事务内自己的写入应该对自己后续的读可见（基本 MVCC 保证），不应该出现这种情况。比较可能的方向是 MySQL 对并发 `INSERT ... ON DUPLICATE KEY UPDATE` 撞同一唯一键时的锁等待行为，与该事务更早建立的 REPEATABLE READ 快照产生了某种交互，这是有一定文档记录但细节微妙的边界行为。**验证方向**：把 `upsert()` 内紧跟 INSERT 之后那条 SELECT 换成加锁读（`SELECT ... FOR UPDATE`），或者给这个方法显式设置 `READ_COMMITTED` 隔离级别做对照实验——如果现象消失就基本坐实快照过期理论。
**影响**：目前只在"同一学生同月账单被并发生成"这个相对少见的场景触发（比如管理员手滑连点两次"生成账单"按钮），不会产生重复账单（唯一约束仍然保护了数据一致性），但会让其中一次请求收到一个容易让人困惑的 500 错误。
**建议**：按上面的验证方向先定位根因，再决定修复方式（更可能是调整这段代码的隔离级别或改成加锁读，而不是动 schema）。
**代码**：`billing/dao/JdbcMonthlyBillDao.java` `upsert`；`billing/service/BillGenerationService.java` `generateBill`；回归测试已写好但禁用：`course/service/CourseConsumptionConcurrencyTest.java` `concurrentGenerateBillForSameStudentAndMonthProducesExactlyOneBill`。

## 2026-10-25 补充发现 · CI/CD 自动化

> 来源：用户主动提出"要不要把 E2E 接入 CI、PR 合并后自动部署"的讨论，评估后决定暂缓，记录成一条正式诊断以免遗忘。

### #77 · 中 — E2E 测试仍未接入 CI，部署仍是纯人工触发，尚不具备"自动化 CI/CD"的条件
**现象**：#44/#46 已经把后端/前端单元测试接入 CI（`.github/workflows/ci.yml`：PR 和合并到 main 时跑 `mvn test` + `tsc -b` + `vitest run`），但 Playwright E2E 测试（`frontend/e2e/*.spec.ts` 4 条 spec）仍然只能本地手动跑（`cd frontend && pnpm test:e2e`），不属于 CI 任何阶段——`frontend/e2e/README.md` 写明"不负责 CI 接入"是诊断 #46 当初的范围外决定，但 #44 落地时也没有把这部分补上。部署（`deploy.sh`）仍然是人工登录生产服务器手动执行，合并到 main 和实际上线之间没有任何自动化关联。
**讨论过程**：
1. **E2E 接入 CI 本身的工程量**：现有 `playwright.config.ts` 假定本地标准 dev 环境（MySQL/MinIO/后端/前端常驻）已经在跑；GitHub Actions runner 是全新空白机器，需要新增 MySQL/MinIO service containers、后端构建+启动+等 Flyway 迁移、跑一次 `SeedCommandLineRunner` 建测试账号、前端构建+起服务、`playwright install --with-deps chromium`，比现有两个单元测试 job 复杂不少，且每次触发都会明显拖慢 CI 时长，还要决定挂在"每个 PR"还是"只在合并到 main 后"。
2. **自动部署的风险**：现有 E2E 套件是诊断 #46 定位的"最小可用冒烟骨架"，只有登录/核心链路/消课/家长分享 4 条 spec，覆盖面远够不上"全面回归"。拿它当"测试通过就自动部署到生产"的唯一闸门，意味着任何没被这 4 条 spec 覆盖到的真实 bug 会无人干预地直接上线到真实试用机构（已有真实数据和日常使用，见 [[project_first_pilot_institution]]），风险敞口比现在"人工跑 `deploy.sh`、盯着输出确认"更大。另外无论是 push 式（GitHub Actions SSH 进服务器，需要开放入站访问+把部署密钥放进 GitHub Secrets）还是 pull 式（服务器装 self-hosted runner 常驻进程主动拉任务），都是新增的安全信任边界，需要专门评估，不是顺手就能接的小事。
**用户决策**：当前机构规模/业务阶段暂时用不到这套自动化，标记为中优先级，**不在当前阶段实现**；等后续有 bandwidth 时再做，且届时应该先尽可能把 E2E 测试覆盖面做厚（覆盖更多真实业务场景和边界情况），测试套件的 confidence 建立起来之后，才更适合大胆引入"测试通过即自动部署"这种更激进的自动化，不建议在当前仅 4 条冒烟 spec 的覆盖水平下就上生产自动部署。
**建议（后续真正要做时的方向）**：
- 分两步走，不要一步到位：第一步只接"PR/合并到 main 时自动跑 E2E"（不涉及部署），先解决"E2E 写了但没人记得手动跑"这个当前的真实问题；第二步等 E2E 覆盖面和长期稳定性都建立起信心后，再评估自动部署。
- 自动部署即使到时候要做，也建议至少加一道人工审批关卡（比如 GitHub Environments 的 required reviewer：CI 自动跑完测试、构建好镜像，但真正执行 `deploy.sh` 前仍由人工点一下确认），不建议做"测试一过、零人工介入"的全自动部署。
- 触发生产部署的技术方案倾向 self-hosted runner（服务器主动拉任务，不需要对外开放入站 SSH、不需要把部署密钥放进 GitHub Secrets），优于直接 SSH push 式部署。
**代码**：`.github/workflows/ci.yml`；`frontend/playwright.config.ts`、`frontend/e2e/*.spec.ts`；`deploy.sh`。

## 2026-10-27 补充发现 · 学年批量晋级向导 review 衍生诊断

> 来源：PR #46（学年批量晋级向导）code review 过程中，独立 review agent 发现的问题，经 fork 二次核实确认属于全仓库既有架构约定/历史遗留，不是该 PR 引入的回归，故未在该 PR 内顺带修复，记录为正式诊断。

### #78 · 中 — 后端业务异常的详细错误信息无法传达到前端，用户只能看到裸的状态码
**现象**：`RosterExceptionHandler` 里全部 17 个业务异常处理方法清一色是"空方法体 + `@ResponseStatus`"模式（如 `handleInvalidTeachingUnitRequest`），响应体永远为空；前端 `api/client.ts` 的 `apiFetch` 在 `!res.ok` 时直接 `throw new ApiError(res.status, \`请求失败（${res.status}）\`)`，从不读取失败响应的 body。两边叠加，后端抛出的任何业务异常消息（如 `AnnualPromotionService` 环检测报错里精心写的"检测到循环的晋级链：A、B、C"）实际永远无法到达用户，前端只能展示"请求失败（400）"这种无信息量的提示。
**影响**：这是架构级的既有限制，覆盖全部 17 种业务异常类型，不是单个功能的 bug；但在"学年批量晋级"这类把详细报错当作核心安全机制卖点的功能上，代价被放大——管理员提交一个有环的晋级链，看不出到底是哪几个班级冲突，只能靠猜或者找人翻后端日志。
**建议**：分两步改：① `RosterExceptionHandler` 的 17 个异常处理方法从"空方法"改成返回 `{"message": ex.getMessage()}` 这样的结构化 body；② 前端 `apiFetch` 在 `!res.ok` 时先尝试读取 body 解析出 `message` 字段，解析失败再退回现有的通用文案，保证向后兼容。需要先过一遍这 17 处异常消息的措辞（目前部分是英文/偏内部实现细节，如 `"Teaching unit not found: " + unitId`），确认哪些适合直接展示给终端用户，这部分属于产品决策，不是纯技术活。
**代码**：`roster/web/RosterExceptionHandler.java`（17 个 `@ExceptionHandler` 方法）；`frontend/src/api/client.ts` `apiFetch`。

### #79 · 中 — 托管班转班/晋级不检查目标班级是否已停用（潜伏风险，当前无触发路径）
**现象**：学生转班的核心校验 `AdminStudentService.validateTeachingUnitAssignment` 和新上线的 `AnnualPromotionService.requireMonthlyUnitInInstitution` 都只检查机构归属和 `billingMode`，不检查 `TeachingUnit.active()`——理论上可以把学生转入/晋级进一个已停用的托管班。但往下深挖一层发现：**托管班（MONTHLY）在当前管理后台 UI 上根本没有"停用"入口**（`AdminTeachingUnitsModule.tsx` 的停用按钮和状态列只对 `billingMode === 'LESSON_COUNT'` 显示），只有课外课能被停用。后端 PATCH 接口本身并未按 billingMode 限制 `active` 字段（`AdminTeachingUnitService.update` 对 `request.active()` 一视同仁），只是前端目前没开这个口子。
**影响**：这是一个"潜伏"而非"活跃"风险——现状下不会被真实触发，因为产品里没有任何正常操作路径能把一个托管班变成已停用状态。但如果以后给托管班也加上停用功能（这其实是合理的产品需求，比如某个托管班这学期不开了），到时候转班和晋级这两处校验会立刻变成能被真实触发的 bug：学生可能被转进/晋级进一个管理员认为"已关闭"的班级。
**建议**：暂不需要现在修复，但建议在给托管班加"停用"功能的同一个 PR 里，顺带给 `validateTeachingUnitAssignment` 和 `AnnualPromotionService.requireMonthlyUnitInInstitution` 补上 `active` 检查，避免这个口子一开就带着旧校验漏洞上线。
**代码**：`admin/service/AdminStudentService.java` `validateTeachingUnitAssignment`；`unit/service/AnnualPromotionService.java` `requireMonthlyUnitInInstitution`；`frontend/src/pages/AdminTeachingUnitsModule.tsx`（停用入口按 `isLessonCount` 隐藏）。

### #80 · 中 — 批量写操作统一采用逐条循环 update，而非批量/批处理语句
**现象**：全仓库 `grep -rn "batchUpdate"` 零命中，`BillGenerationService`、`AnnualPromotionService` 等所有涉及"对一批记录做同样更新"的场景，统一写法都是 for 循环里对每条记录单独调用一次 DAO 的 `update` 方法，没有用 JDBC 批处理（`addBatch`/`executeBatch`）或单条 SQL 的批量更新语句。
**影响**：这是现有代码库一致的写法规范，不是某个功能独有的缺陷。当前机构规模（诊断 #34 提到的"单机构学生数破千"量级）下，单事务内循环 update 的性能代价可忽略；但如果机构规模持续增长，这类接口（尤其是"一键生成账单"#34、"学年批量晋级"）会线性增加数据库往返次数，和 #34/#36 指出的 N+1 查询问题属于同一类"现在不是问题，规模变大后会累积放大"的技术债。
**建议**：不建议现在单独修复（引入批量写法反而是脱离现有代码风格的新抽象，应该和 #34/#36/#37 的性能优化放在一起通盘考虑，而不是逐个功能各自为战）。等评估 #34/#36 这类高优先级性能问题时，一并确立"批量写操作"的统一规范（比如引入 `batchUpdate` 这样的 DAO 方法约定），再回头把已有的循环写法迁移过去。
**代码**：`billing/service/BillGenerationService.java`；`unit/service/AnnualPromotionService.java` `execute`（`studentDao.update` 循环）。
