### #01 · 高风险 — 课外课消课完全不校验余额 ✅ 已修复（2026-10-03）
**现象**：系统有「充值」和「消课」概念，但消课时从不检查余额，哪怕余额为负也能继续，唯一反馈是对账单上的负数。
**影响**：点名默认全勾，容易在未提醒续费时持续产生「欠课时」，只能靠人工翻账单发现。
**代码**（2026-10-12 校正行号）：`course/service/CourseConsumptionService.java:101` `recordBatchConsumption`（仍然无余额检查，确认行为没有变化）；`CourseAccountService.java:76` `getStatement`（余额仅用于展示）。
**已做**：`listRosterForCourse` 新增按课程计算的 `balance`，`CourseConsumptionPage.tsx` 点名列表里余额 ≤0 标红提示，不阻断消课（按用户决策，暂不做阻断开关）。

### #02 · 高风险 — 同一动作，三套互不相通的财务处理 ✅ 已修复（架构统一，按本诊断当初的中长期建议实现）
**现象（历史）**：「确认上了一节课外课」的财务处理曾经完全取决于该生是否同时在托管班：无托管班→预充值/余额模式，无正式账单；有托管班→不允许预充值（`recharge` 对有班级的学生抛 `RechargeNotAllowedException`），费用月底自动追加进托管账单附加费。
**影响（历史）**：财务人员要理解两套规则，同类学生收费体验不一致，容易引发核账混乱和家长困惑。
**已做（完整架构统一，不只是短期缓解）**：`RechargeNotAllowedException` 已从代码中完全移除——**现在任何报了课外课的学生都可以充值，不再区分是否同时在托管班**。消课是否计费统一由 `CourseAccountService.classifyConsumptions`/`classifyForCourse` 按"学生+课程"把充值和消课事件按时间顺序回放判定：充值余额覆盖的消课不收费，未覆盖的部分在 `BillGenerationService.generateBill` 生成月度账单时自动计入"课外课附加费"一行——**这套结算规则现在对所有学生统一适用**，`BillGenerationService.computeCourseConsumptionRows` 头部注释明确写着"覆盖判定的唯一权威来源是 CourseAccountService.classifyConsumptions——它对任何学生都适用"。连带效果：纯课外课学生现在也会生成正式的月度账单（学费/餐费记 0，只汇总未覆盖的课外课费用），不再是"无正式账单"。
**遗留的不一致**：家长分享页对双重身份学生仍只展示轻量的"当日课外课情况"（不展示充值/余额），`PublicShareService`/`CourseAccountService.getCourseActivity` 处的代码注释仍写着"这类学生从不预充值，余额概念不成立"——这句注释已经和当前的充值规则不一致，是代码注释没有跟上架构统一的遗留问题，不代表产品决策，建议找时间订正注释并评估是否要把余额信息也展示给这类学生的家长看。
**代码**：`CourseAccountService.java` `recharge`（已无身份限制）/`classifyConsumptions`/`classifyForCourse`；`BillGenerationService.java` `computeCourseConsumptionRows`/`generateBill`/`generateBillsForInstitution`（遍历全机构所有在读学生，不分身份）。

### #03 · 高风险 — 纯课外课学生在「账单管理」完全不可见 ✅ 已修复（教学单元合并时顺带解决）
**现象**：账单管理严格按托管班组织，纯课外课学生没有班级，结构性地不会出现。唯一入口是「学生总览」操作列的按钮。
**影响**：月度财务核对时容易完全遗漏这部分学生的欠费风险，尤其叠加 #01 后更隐蔽。
**建议**：在账单管理页顶部增加「纯课外课学生」分区，至少汇总展示余额异常学生。
**代码**：`AdminBillingModule.tsx`（按班级分组）；`AdminStudentsModule.tsx`（按钮仅对 `offCampusOnly` 展示）。
**已做**：托管班+课外课合并为统一教学单元模型后，`BillGenerationService.generateBill` 不再因缺少班级 404，`getBillOverview`/`getBillOverviewAllMonths` 改为遍历全部学生，纯课外课学生自然出现（学费/餐费记 0，只汇总课外课消课附加费）。

### #07 · 中 — 机构功能开关只是「前端软开关」⚠️ 部分缓解（仅创建环节，非全面拦截，待与用户确认是否算已解决）
**现象**：关闭托管/课外课只隐藏导航入口，底层接口无机构级拦截，理论上仍可被直接调用成功。
**2026-10-12 核实发现**：`AdminTeachingUnitService.create` 现在会在**创建**教学单元时校验对应功能开关（`!institution.custodyEnabled()` / `!institution.offCampusEnabled()` 时抛 `FeatureDisabledException`），这是本次核实时新发现的、诊断文档此前没有记录的校验。但这只拦住"新建"这一个动作——对**已存在**的班级/课程继续打卡、布置任务、点名消课等日常操作，后端仍然没有按机构功能开关做拦截（即关闭托管后，已有托管班的日常看板操作接口不受影响）。核心问题"关闭开关不能让已有功能停止工作"仍然成立，不建议标记为完全修复。
**建议**：暂不改造，但在内部文档标注「开关目前只在创建新单元时生效，不影响已有数据的日常操作」；接入对外 API 时再补全面的后端校验。
**代码**：`AdminInstitutionService.java` `updateFeatureFlags`（仅校验不能同时为 false）；`AdminTeachingUnitService.java` `create`（新发现的创建时校验）；`AdminSidebar.tsx` `isModuleHidden`（纯前端判断）。

## 第二轮诊断（2026-10-13）· 一、业务与产品缺口

> 来源：资深教辅机构从业人员 + 资深产品经理两份独立审查，重合发现已合并。

### #10 · 高 — 增长飞轮的核心动作"引导关注公众号"在产品里没有任何实际触点
**现象**：商业模式明确写着家长端靠"关注公众号"转化，但分享页、分享海报全文搜索"公众号"/二维码零命中；家长扫码只会看到孩子的学习报告或课外课对账单，看完就关掉。纯课外课学生查看对账单（家长关注度最高的时刻之一）同样没有任何关注引导。
**影响**：`StudentShareViewLog` 统计的"查看次数"和商业化真正要的"涨公众号粉丝"是两件事，增长目标无法被产品验证或推动，整套增长策略停留在文档层面。
**建议**：在分享页/海报、尤其是课外课对账单页加一个真实可配置的公众号关注引导位（二维码+文案）。
**代码**：`ParentSharePage.tsx`、`SharePosterModal`/`ShareLinkModal`。

### #11 · 高 — 账单欠费提醒夹杂大量 ¥0.00 空账单，稀释真实欠费信号 ✅ 已修复（2026-10-13）
**现象**：纯课外课学生当月消课全被充值覆盖时仍会生成一条 ¥0.00 的账单且状态为"未缴费"；机构总览"账单欠费提醒"卡片按生成顺序平铺全部未缴费记录，无金额过滤/排序/高度上限。实测环境 42 笔欠费里近一半是 ¥0.00，且和真实大额欠费共用同一个橙色"●未缴费"徽标。
**影响**：真正该催收的对象被淹没在无意义的 0 元提醒里，前台要逐条点开才能分清，随数据积累只会越来越严重。
**已做**：`BillGenerationService.getUnpaidBillSummary` 过滤条件新增 `totalAmount > 0`，¥0.00 账单不再计入"未缴费"统计（账单本身仍正常落库，`AdminBillingModule` 逐条列表不受影响，零元账单继续原样展示）；`UnpaidBillsCard.tsx` 对拿到的行按金额降序排序，并加滚动高度上限避免卡片被撑爆。补充了后端单元测试验证零元/非零账单的过滤行为。
**代码**：`BillGenerationService.java` `getUnpaidBillSummary`；`UnpaidBillsCard.tsx`。

### #12 · 高 — 全链路没有任何主动触达能力，平台到机构、机构到家长都靠人工肉眼+微信喊话
**现象**：系统没有短信/模板消息/企业微信机器人等任何外发通知渠道。机构到期/欠费提醒只在平台管理员列表/机构总览页肉眼可见；账单生成后家长收不到任何提醒，全靠教师在微信群手动喊话。
**影响**：续费流失和收款逾期无法被动发现，收款周期被教师个人勤勉度左右，机构数变多后平台管理员会漏看，直接影响订阅收入和现金流。
**建议**：至少给"到期前 N 天""欠费超过阈值"两类场景接一条自动短信/企业微信机器人通知；评估账单生成/超期是否也能通知家长。

### #13 · 高 — 学生停用/离校没有退费与余额清算流程
**现象**：停用学生只是把 `enrolled` 置为 false，不检查未缴账单、不检查课外课充值余额，全系统没有"退费"概念。
**真实场景**：学生转学时还剩若干课外课课时没上完，或多收了半个月餐费，家长要求退钱，机构只能线下用现金/转账解决，系统账目和实际资金流脱节。
**建议**：停用学生时提示未结清账单和课外课余额，补一个退费登记入口（哪怕只是备注金额，不做真实退款对接）。
**代码**：`AdminStudentsModule.tsx` `handleConfirmDeactivate`；`AdminStudentController` 停用接口。

### #14 · 高 — 账单催收能力薄弱：无逾期排序/批量操作，收款不记录方式也不支持部分收款 ⚠️ 部分修复（2026-10-13，按用户决策缩小范围）
**现象**：账单管理页 42 笔欠费按生成顺序平铺，没有逾期天数排序、批量操作、导出；"是否已缴费"只是一个布尔开关，没有现金/微信/支付宝/银行转账的区分字段，也不能登记部分收款。
**真实场景**：家长先转一半学费说"过两天补齐"，前台要么硬标"未缴费"忘记已收部分，要么标"已缴费"但实际没收全；月末对账时无法核对各渠道流水分别收了多少，现金环节尤其容易出现经手人昧款难发现的风险。
**范围确认（已与用户确认）**：本次只做 UI 层面的排序/逾期展示 + 收款方式字段，不做部分收款登记（即不做金额拆分/多次收款记录），这部分仍是遗留缺口。
**已做**：`monthly_bill` 新增 `payment_method` 字段（现金/微信/支付宝/银行转账），标记已缴费时必须选择收款方式；`BillOverviewRow`/`UnpaidBillRow` 新增 `overdueDays`（约定到期日=账单所属月份月底）；`AdminBillingModule.tsx` 加逾期天数列和排序（默认/逾期优先/金额优先）。后端批量标记接口（`PATCH /admin/bills/batch-paid`）已实现并保留。
**后续发现的 UX 问题及处理**：批量标记上线后，用户发现页面同时存在"批量标记已缴费"和"一键生成本月账单"两个入口，但学生勾选框（checkbox）只对前者生效、对后者无效，容易造成误解。讨论后决定**暂时从前端移除批量标记已缴费功能和对应的 checkbox**（后端接口保留不删），等真实使用一段时间、有明确业务反馈后再重新评估是否需要、以及如何统一交互。
**代码**：`AdminBillingModule.tsx`、`billing/domain/PaymentMethod.java`、`MonthlyBillDao`/`JdbcMonthlyBillDao`（`setPaid` 签名加收款方式）、`BillGenerationService.java`（`overdueDaysFor`/批量标记方法保留）。

### #15 · 中 — 平台方没有机构"健康度"指标，到期日是滞后的流失信号
**现象**：平台管理页机构列表只有学生/班级/教师数、今日查看人数、到期状态，没有把登录频率、功能使用深度、欠费率、学生增减趋势综合成一个分数。
**影响**：机构可能提前一两个月就已经"不活跃"，等到期才发现为时已晚，错过挽留窗口。
**建议**：综合近 30 天登录/消课/打卡频次、欠费占比，做一个简单的健康度分级（红/黄/绿）。

### #16 · 中 — 请假扣学费的"应出勤工作日"没有排除法定节假日/寒暑假
**现象**：`BillGenerationService.countWeekdays` 只排除周六日，国庆/春节/寒暑假等机构实际放假的工作日照常算"应出勤"；家长没主动登记"请假"时，这些天仍按应出勤收费。
**影响**：法定节假日越多的月份，家长实收学费越"亏"，容易引发投诉和对账纠纷，机构解释不清。
**建议**：引入机构级节假日/放假日历，计算应出勤天数时扣除。
**代码**：`BillGenerationService.java` `countWeekdays`。

### #17 · 中 — 转班（换托管班）没有费用结算提示，按整月现班级单价计费
**现象**：学生编辑页的托管班是个下拉框，切换后直接生效；`generateBill` 只看当前 `teachingUnitId` 对应班级单价整月计算，不管这个月是不是月中才转过来的。
**真实场景**：学生月中从托管 A 转到托管 B，两班学费不同，月底账单只按"最终所在"的托管 B 单价整月收费，前半个月在托管 A 的事实被完全忽略。
**建议**：转班时提示当月已有考勤数据，账单生成逻辑按班级分段计费或人工核实金额。
**代码**：`BillGenerationService.java` `generateBill`。

### #18 · 中 — 优惠/折扣机制完全缺失
**现象**：`ClassBillingRate` 只有月学费+日餐费两个数字字段，账单管理里唯一的灵活调整是"本月托管费金额"这个一次性覆盖值，无法配置"老带新立减""多孩优惠""续费送课"等常见促销规则。
**影响**：促销活动无法规模化执行，容易改错/改漏，也没有历史折扣记录可追溯，财务和运营对不上折扣口径。
**建议**：账单上增加可追溯的折扣行（而非直接覆盖总价），支持常见折扣类型模板。

### #19 · 中 — "只登记续费不扣款"纯人工续费流程，机构规模化后会成为瓶颈
**现象**：续费完全是平台管理员手工打电话+登记套餐，没有微信支付/支付宝预授权，也没有到期自动限流或宽限期机制。
**影响**：机构数量增长后这套纯人工流程会成为规模化瓶颈，收入确认延迟且容易出现"忘记跟进"导致的隐性流失。
**建议**：短期先加自动化提醒（见 #12），中期评估是否接入自助续费链接（不一定要做扣款网关）。

### #20 · 中 — 定价完全扁平，没有用量分层或数据支撑调价
**现象**：订阅价格与机构规模（学生数/教师数/消课量）无关，系统虽然有这些用量数据，但从未汇总成报表反馈给平台方做定价参考。
**影响**：小机构和大机构同价，要么小机构觉得贵流失，要么大机构的边际成本没有被覆盖，长期影响客单价和续费率。
**建议**：先做一张"机构规模 vs 当前订阅价"的内部报表，再评估分层定价。

### #21 · 中 — 家长分享页增长机制单薄，没有裂变设计
**现象**：唯一的增长指标是"查看次数"（按学生+自然日去重），没有家长间转发、排行榜、连续打卡激励、邀请解锁等任何社交裂变机制。
**影响**：分享页曝光量只能线性增长（一个孩子一个家长），没有放大器，#10 提到的公众号转化量级会长期偏低。
**建议**：加"连续打卡天数"展示、鼓励家长截图发朋友圈的文案钩子，低成本提升裂变系数。

### #22 · 中 — 收入快照没有趋势/环比，管理员看不出"在变好还是变差"
**现象**：机构总览"收入快照"只展示当月托管费实收/应收百分比和本月课外课消课次数，没有近 3-6 个月的趋势线或环比数字。
**影响**：单月快照无法支撑决策——管理员不知道收款率是在改善还是恶化，也看不出哪个月是旺季/淡季。
**建议**：加最近 6 个月实收率趋势的简单折线/柱状图。

### #23 · 中 — 新机构 Onboarding 只有被动的"帮助"文档弹窗，没有主动引导
**现象**：`HelpModal` 以静态步骤文字列出"改密码→配置机构→建教师→建教学单元→录学生"，但入口要自己点"帮助"按钮，没有首次登录强制引导、没有进度追踪、空状态页也没有"去建一个吧"的 CTA。
**影响**：机构管理员多是非技术背景，被动文档容易被忽略，真实试用机构上线后如果没人带着走一遍，容易卡在第一步放弃。
**建议**：首次登录弹一个分步引导（可跳过），关键模块空列表时加引导按钮。

### #24 · 中 — 教师提成/工资结算完全不在系统范围内
**现象**：全系统没有任何与教师薪酬挂钩的统计或页面，"任务完成情况"只统计学生侧数据。
**真实场景**：机构给托管老师按带班人数提成、给课外课老师按课时费结算工资，目前都要老板自己拿 Excel 对着系统里的学生数/消课记录重新算一遍。
**建议**：至少把"教师带生数""课外课消课次数"等已有统计导出，供机构自行核算提成，不必做复杂薪酬引擎。

### #25 · 中 — 课外课只有"到/不到"，没有请假/补课概念
**现象**：点名消课只有勾选/不勾选两种状态，不勾选的学生不生成任何记录（呼应 #08），系统全局没有"补课/调课"功能。
**真实场景**：请假的学生希望"这节课不算消耗、找时间补上"，但系统里请假和"忘记点名"完全无法区分，老师私下口头承诺补课但系统没有任何记录，容易扯皮。
**建议**：课外课点名增加"请假"状态（不计消课），并提供轻量的"待补课"标记。

### #26 · 低 — 多校区/连锁机构没有汇总视图
**现象**：`Institution` 是唯一的顶层实体，没有总部-分校层级，平台管理员列表是逐机构平铺展示。
**真实场景**：同一个老板名下开了多家分校（行业里很常见的扩张路径），现在必须拿多个独立账号登录多次才能看完当月总营收，规模化客户体验不到"集团管理"的价值。
**建议**：暂不建议改造，等出现真实连锁型客户需求后再评估引入"集团"概念或跨机构汇总报表。

### #27 · 低 — 忘记密码无法自助找回在机构规模化后会变成持续客服成本
**现象**：改密接口要求必须提供旧密码（这是[业务流程.md 流程八](./business/业务流程.md#流程八账号与权限)已记录的已知限制，非新发现），全系统没有任何重置入口。
**影响**：目前机构少还能人工兜底，随着试用机构增多，会变成频繁打扰开发/运维的客服工单，且全靠人工改库存在误操作和信任成本。
**建议**：至少给机构管理员一个"重置下属教师密码"的后台按钮，不必做自助找回邮箱/短信验证。

### #28 · 低 — 没有发票/收据功能
**现象**：全系统搜索不到发票、收据相关的任何代码或页面。
**真实场景**：家长问"能不能给张收据"，机构只能手写或用外部工具另外生成，和系统账单对不上编号，一旦家长质疑金额要翻两处资料核对。
**建议**：账单详情增加可打印/可导出的简单收据模板，暂不对接正式税务发票。

### #29 · 低 — 账单无法导出/打印
**现象**：账单管理页只能在网页上逐条查看/标记，没有导出 Excel、没有生成可打印的对账单。
**影响**：机构做月度财务核对或给家长开具凭证时缺少标准化产物，规模变大后是明显的刚需缺口。
**建议**：加按月/按班级导出 Excel 的能力。

### #30 · 低 — 教师工作量/带班质量数据未被用来做管理决策
**现象**：总览页"按老师分布"只显示带班人数，任务完成率、平均评分、消课及时率等按教师维度的对比数据完全没有呈现。
**影响**：管理员想知道"谁带得好谁带得差"只能凭感觉，招人/排班/绩效决策缺数据支撑。
**建议**：加一张"教师工作量与质量对比"表，复用已有打卡/评分数据即可，是低成本高价值的报表缺口。

### #31 · 低 — 课时预警卡片无一键触达家长能力
**现象**：课时不足预警卡片只有"去充值"按钮（管理员自己操作），没有"提醒家长"的分享链接或话术一键发送功能。
**影响**：管理员发现预警后仍要手动微信联系家长催费，预警本身没有缩短"发现问题到解决问题"的链路。
**建议**：预警卡片加一个"复制催费话术"或直接带上该生分享链接的按钮。

### #32 · 低 — 没有合同/协议管理
**现象**：全系统搜索不到合同、协议相关的任何功能，报名/续费通常要签的纸质或电子协议留存完全在系统外。
**影响**：对于走规范化、可审计方向的机构，续费纠纷时拿不出电子留痕。
**建议**：优先级低，可作为后续结合电子签章的扩展功能，暂不建议近期投入。

## 第二轮诊断（2026-10-13）· 二、技术架构与可扩展性

> 来源：资深架构师审查，全程用代码知识图谱（`transitive_loop_depth`/`linear_scan_in_loop` 等指标）定位真实热点，并核对了全部 Flyway migration 的索引情况，证据均为 file:line 或 qualified_name，非主观猜测。**#33 是一个现在就成立的真实代码缺陷，建议优先单独修复**，其余按"多大体量会成为问题"的紧迫度排列。

### #33 · 高（现在就成立的代码缺陷） — 批量生成账单时 `@Transactional` 被自调用绕过，循环内写操作失去事务保护 ✅ 已修复（2026-10-13）
**现象**：`generateBill`（`BillGenerationService.java:201-202`）标了 `@Transactional`，但批量入口 `generateBillsForInstitution` 在**同一个类内部直接调用** `generateBill(...)`，Spring AOP 代理拦截不到类内自调用，事务注解实际不生效。
**影响**：`monthly_bill` upsert 成功但明细表（附加费/用餐/请假行）插入失败时不会回滚，账单金额和明细行可能对不上；不依赖数据量，现在就成立。
**已做**：给 `BillGenerationService` 注入一个指向自己的 `@Lazy` 代理（`self`），`generateBillsForClass`/`generateBillsForInstitution`/3 参重载的 `generateBill` 一律改成调用 `self.generateBill(...)` 而不是 `this.generateBill(...)`，让每次调用都重新经过代理，`@Transactional` 真正生效。新增 `BillGenerationTransactionalityTest`：用 `@SpyBean` 强制 `MonthlyBillMealLineDao.insert` 在批量生成中途抛异常，验证修复前账单主表会残留（RED），修复后整笔回滚（GREEN）。
**代码**：`BillGenerationService.java`（新增 `self` 字段+构造参数，`generateBill`/`generateBillsForClass`/`generateBillsForInstitution` 调用点）；`billing/service/BillGenerationTransactionalityTest.java`。

### #34 · 高 — "一键生成账单"同步跑全机构学生，且每个学生都做全历史回放
**现象**：`generateBillsForInstitution`（`transitive_loop_depth=4`）在一次 HTTP 请求内对筛选出的全部学生逐个调用 `generateBill`→`computeCourseConsumptionRows`→`CourseAccountService.classifyConsumptions`，后者对该学生**全部历史**充值+消课记录各做一次全表查询再在内存回放排序。
**会在什么体量下出问题**：单机构学生数破千、或机构运营年限变长导致单生历史记录数变多时，一次点击所需的 DB 往返次数和单次回放耗时同时增长，容易超过 Nginx/浏览器超时。
**建议**：改成异步任务+进度轮询；给 `classifyConsumptions` 引入按月的余额快照，避免每次都从头回放全部历史。

### #35 · 高 — 账单总览/总览所有月份接口对全机构学生做 N+1 查询，且无分页
**现象**：`getBillOverview`/`getBillOverviewAllMonths`（均 `transitive_loop_depth=4`）按教学单元遍历，内部对每个学生单独查 `monthlyBillDao.findAllByStudentId`；`StudentOverviewOrder.computeFirstCourseNames` 还对每个纯课外课学生单独查 `enrollmentDao.findAllByStudentId`。
**会在什么体量下出问题**：单机构学生数破千时，账单管理/学生总览每次打开就是成百上千次独立 DB 往返，返回列表本身也无分页。
**建议**：用 `IN` 批量查询替代逐条查询，总览列表加分页。

### #36 · 高 — 管理后台"今日概览"对每个托管班做 4 次独立查询
**现象**：`AdminStatsService.getTodaySnapshot`（`linear_scan_in_loop=1`）for 循环遍历机构全部托管班，每个班单独查到校/用餐/请假/任务 4 张表，无批量查询。
**会在什么体量下出问题**：单机构班级数从十几涨到上百时，打开一次首页就要 400+ 次 DB round trip；这是管理员登录后最先看到、刷新最频繁的页面。
**建议**：按 `institutionId` 一次性批量查当天记录，内存按 unit 分组聚合。

### #37 · 中高 — "低结余预警"对全机构历史记录做嵌套扫描，接近 O(n²)
**现象**：`CourseAccountService.getLowBalanceEntries` 先取出全部历史充值+消课记录，再对每个"学生+课程"组合重新扫一遍这两个全量列表算余额。
**会在什么体量下出问题**：机构历史充值/消课记录从几百条涨到几万条后，嵌套扫描的耗时呈平方级增长，且每次请求都重算、无缓存。
**建议**：一次 `groupingBy` 分组统计代替逐 key 重新过滤；长期应下推到 SQL 层 `GROUP BY`。
**代码**：`CourseAccountService.java:113-150`。

### #38 · 中 — 无缓存层，多机构共享单一 MySQL 实例，没有隔离
**现象**：技术栈无 Redis；总览类接口（今日概览/低结余/欠费统计/营收快照）每次请求都直接命中 MySQL 做全量聚合，所有机构靠 `institution_id` 过滤共享同一套表、同一实例。
**会在什么体量下出问题**：机构数破百、且出现一两个数据量明显更大的机构时，大机构的慢查询会占用数据库资源，拖慢同实例上其它小机构的请求（噪声邻居效应）。
**建议**：给总览类接口加短 TTL 缓存（哪怕先用进程内 Caffeine），为后续接入 Redis 留好接口边界。

### #39 · 中 — 单体单实例部署，水平扩展路径不清晰，连接池未显式调优
**现象**：`docker-compose.yml`/`docker-compose.prod.yml` 只定义一个 `backend` 容器，无多副本配置；`application.yml` 未显式配置 HikariCP 参数（默认 `maximum-pool-size=10`），而 #34-#37 的热点单次请求可能连续占用连接执行几十到上百次串行查询，容易把默认连接池耗尽。
**会在什么体量下出问题**：并发在线人数/QPS 触及单机 CPU、内存或默认连接池上限时，通常对应机构数上百、同时在线上千；容器重启期间也是单点故障，整个平台不可用。
**建议**：提前验证"Nginx 反代多个 backend 副本"的可行性，并结合压测结果显式配置 HikariCP 连接数上限（副本数 × 单实例连接数不超过 MySQL `max_connections`）。

### #40 · 中 — JWT 30 天长有效期，无撤销/黑名单机制
**现象**：`JwtService.java:15` `TOKEN_TTL = Duration.ofDays(30)`，`parseToken` 只校验签名和过期时间，不查询账号是否已禁用/已改密。
**影响**：教师离职当天被后台禁用，但其设备上的 token 仍可用 30 天——已有真实机构数据上线，这是安全/合规风险，机构数、教师数变多后出现频率线性增加。
**建议**：引入 token 版本号或黑名单表，登录态校验时附带检查，不必依赖 Redis，一张 MySQL 表即可起步。

### #41 · 中 — 打卡/用餐/请假/每日任务四张高频表只有单列 FK 索引，缺复合索引
**现象**：`student_arrival_checkin`/`student_meal_record`/`daily_task`/`student_leave_record` 均只声明外键约束（MySQL 自动生成单列索引），但查询模式是 `findAllByTeachingUnitIdAndDate(unitId, date)` 这种双条件过滤，没有显式 `(teaching_unit_id, 日期)` 复合索引。
**会在什么体量下出问题**：单个托管班运营 3-5 年后，同一 `teaching_unit_id` 下历史记录积累到几千条，只能靠单列索引做范围扫描再过滤日期，逐年劣化。
**建议**：给这几张表加 `(teaching_unit_id, 对应日期列)` 复合索引。

### #42 · 低中 — 多张纯追加表无归档/分区策略
**现象**：`audit_log`、`course_consumption_record`/`course_recharge_record`、`monthly_bill` 及明细表、`student_share_view_log` 都只插入不删除，没有 TTL 或分区设计；`audit_log` 甚至没有查询 UI，纯粹留痕。
**会在什么体量下出问题**：机构数到百级、单机构运营 3-5 年后，这几张表行数可能达到千万级，单表体积膨胀影响全库备份/恢复耗时。
**建议**：不急，但建议提前规划按年分表或定期归档到冷存储（尤其 `audit_log`，没有查询需求，最适合归档）。

### #43 · 低 — MinIO 单实例、单 volume，无副本/生命周期策略
**现象**：MinIO 是单容器 `server /data`，没有 distributed mode，也没有对象生命周期规则，所有头像类小文件堆在一个 volume 里。
**影响**：当前体量下存储空间本身不是瓶颈，真正的风险是单点故障——这台机器磁盘损坏会丢失全部机构的头像文件。
**建议**：优先级是补充 `minio_data` volume 的定期异地备份（见运维篇 #55），而非近期考虑扩容或分布式部署。

## 第二轮诊断（2026-10-13）· 四、运维与生产可靠性

> 来源：资深运维工程师审查，实际核对了 `docker-compose*.yml`、`pom.xml`、`application.yml`、`HealthController`、部署脚本、nginx 配置示例等。核实过"机构开通/建教师时明文密码被意外记日志"的疑虑并不成立——真正的问题是全仓库没有任何业务日志（见 #56），而非密码泄露。

### #55 · 高 — 备份从未自动化、从未验证过能恢复
**现象**：`DEPLOY.md` 只写"建议写一个 cron"，部署脚本均未实际配置定时任务，仓库内无 backup 脚本；"安全检查清单"本身就承认这是真实风险。
**影响**：若当前确实没人手动配置 cron，相当于零备份；即使配了，没做过 restore 演练，真正故障时不知道备份能不能用。
**建议**：落地 cron + 异地同步，并每月跑一次真实恢复演练到独立环境验证。

### #56 · 高 — 无可观测性，故障只能靠用户投诉发现
**现象**：`pom.xml` 无 actuator/micrometer/sentry 等依赖；`HealthController.health()` 只是硬编码返回 `{"status":"ok"}`，不探测 DB/MinIO 连通性；全仓库搜 `log.info/log.error/LoggerFactory` 命中 0 处业务日志。
**影响**：账单生成失败、消课异常等问题没有任何自动告警，运维只能等机构反馈或翻容器日志排查，MTTR 高。
**建议**：接入基础 APM/错误上报（如 Sentry）+ 关键业务路径打点日志 + 简单告警（磁盘/进程存活/5xx 比例）。

### #57 · 高 — 登录接口无暴力破解防护
**现象**：`AuthService.login` 仅校验密码匹配后抛异常，无失败次数计数/锁定；nginx 配置示例未配置限速。
**影响**：`/api/auth/login` 可被无限速率尝试撞库，机构管理员/教师账号存在被暴力破解风险。
**建议**：nginx 层加限速，应用层加登录失败锁定（如 5 次/15 分钟）。

### #58 · 高 — 单机单实例架构，RTO/RPO 不可控
**现象**：单台服务器跑 MySQL/MinIO/backend/frontend 全部组件，均无副本；技术架构文档未给出任何容灾预案或量化的恢复时间目标（与架构篇 #38-#39 的扩展性视角互为补充，这里关注的是故障恢复而非性能）。
**影响**：主机硬件故障或磁盘损坏时，恢复完全依赖人工重建服务器+手工执行备份恢复，耗时和数据丢失量都没有上限，叠加 #55 会更严重。
**建议**：至少把 MySQL 逻辑备份自动同步到异地存储，评估是否需要只读从库。

### #59 · 高 — Flyway 迁移无回滚预案，且历史上已有破坏性迁移
**现象**：技术架构文档记载 `V15`/`V17` 是"破坏性迁移，清空旧数据强制重录"；Flyway 社区版不支持 down migration；`DEPLOY.md` 全文未提生产迁移失败的应急步骤。
**影响**：下一次类似的破坏性迁移如果在生产执行中途失败或逻辑有误，唯一恢复手段是整库回退到上一次备份，期间数据全部回滚，且无文档化流程。
**建议**：新增迁移前的"迁移前自动备份"步骤，并书面化失败应急流程（停服→评估→回滚备份或手工补 SQL）。

### #60 · 中 — 部署非零停机，每次更新都有服务中断窗口
**现象**：部署脚本对 backend/frontend 执行 `docker compose build` + `up -d`，单实例重建镜像后直接重启容器，没有蓝绿/滚动策略。
**影响**：每次日常更新（含紧急修复）期间，登录中的家长/教师会短暂遇到 502 或接口不可用。
**建议**：早期体量小可接受，但应在 `DEPLOY.md` 标注预期中断时长，并提示择低峰期发布。

### #61 · 中 — 容器健康检查与依赖等待不完整
**现象**：`docker-compose.yml` 只给 `mysql` 配置了 `healthcheck`，backend/frontend 都没有；backend 对 MinIO 的 `depends_on` 条件是 `service_started` 而非健康检查。
**影响**：MinIO 启动但未真正就绪、或 backend 进程假死时，Compose 无法感知异常，掩盖了"服务名存实亡"的情况。
**建议**：给 backend 补 `/api/health` 的 healthcheck，并让它真实探测 DB/MinIO 连通性。

### #62 · 中 — 容器无资源限制，无隔离
**现象**：三个 `docker-compose*.yml` 文件均未出现 `mem_limit`/`deploy.resources`/`cpus` 等配置。
**影响**：单台服务器上任一容器异常吃满内存/CPU（如慢 SQL 累积）会拖垮同机其它服务，故障互相传染，无硬隔离兜底。
**建议**：按当前体量给 mysql/backend 设置合理的内存上限，防止雪崩。

### #63 · 中 — 日志无轮转、无聚合，磁盘容量缺乏监控
**现象**：未发现任何 logging driver/max-size 配置（Docker 默认 json-file 无限增长），也没有磁盘使用率监控或告警阈值。
**影响**：长期运行后容器日志、MySQL 数据、MinIO 文件都可能无声耗尽磁盘，最终表现为写入失败/服务异常，且提前发现不了。
**建议**：给 Docker daemon 配 `max-size`/`max-file`，加一个简单的 df 阈值告警。

### #64 · 中 — 没有独立的 staging/预发布环境
**现象**：本地开发环境只是开发者本机，`DEPLOY.md`/架构文档均未提及任何接近生产配置的预发布环境。
**影响**：首个机构已有真实生产数据，Flyway 迁移、nginx 配置变更等高风险操作缺少一个"像生产一样"的环境先验证，直接本地过测试就上生产。
**建议**：体量允许时搭一套最小 staging（同版本 MySQL/MinIO），至少跑一遍迁移再上线。

### #65 · 中 — 依赖安全缺乏自动化扫描
**现象**：仓库无 `.github/dependabot.yml`，也没有发现任何 SCA 配置；关键安全组件版本更新完全靠人工。
**影响**：Spring Boot、jjwt 等组件出现 CVE 时不会有任何自动提醒，依赖长期不更新的风险累积。
**建议**：开启 GitHub Dependabot（免费），定期合并安全补丁 PR。

### #66 · 低 — 缺少全局异常处理器，未预期异常无统一出口
**现象**：全仓库只有局部异常处理，没有应用级 `@ControllerAdvice` 兜底；叠加 #56 无日志，未被模块内捕获的异常既不会被记录也不会被统一处理成友好响应。
**影响**：排查线上问题时，意外异常只能从容器日志里翻 stacktrace，没有结构化记录，效率低。
**建议**：加一个最简单的全局 `@RestControllerAdvice` 统一兜底并打印/上报异常。

### #67 · 低 — MinIO 控制台/防火墙等安全基线全靠人工纪律，无代码化校验
**现象**：`DEPLOY.md`"安全检查清单"里"MinIO 端口不要暴露公网""防火墙只放行必要端口"都是纯文字 checklist，没有脚本或自动检测这些规则是否被误改。
**影响**：换人维护、手滑改了一条配置，不会有任何自动化手段提前拦截，只能等被扫描/攻击后才发现。
**建议**：写一个简单的定期自检脚本（探测端口是否公网可达、核对防火墙规则）。
