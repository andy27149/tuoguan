## 一、系统一句话定位

**奕成长课后平台**是面向中小型课后托管/课外课机构的 SaaS 系统：机构管理员在后台搭建教师、班级/课程、学生结构并管理财务，教师在一线完成每日托管看护记录和课外课消课点名，家长通过免登录的分享链接查看孩子的情况，平台方（我方）统一开通机构、跟踪试用/续费状态。

核心业务特征：**同一个学生可以同时是"托管班学生"和"课外课学生"（双重身份）**。课外课本身的计费规则对所有学生一视同仁（充值优先覆盖消课，未覆盖部分月底计入账单），"是否有托管班"只决定账单里要不要额外加学费/餐费（见[第五章](#五课外课计费与结算充值覆盖--月度账单兜底)）——这是理解本系统大部分设计决策的关键。

## 二、角色体系

系统有 3 种真实登录角色 + 1 种隐性角色（无账号体系）：

| 角色 | 枚举值 | 登录方式 | 核心职责 | 主要入口 |
|---|---|---|---|---|
| **机构管理员** | `Role.ADMIN` | 手机号+密码 | 机构结构搭建（教师/教学单元/学生）、定价、账单、运营数据只读看板、机构基础信息 | 管理后台（侧边栏 8 模块） |
| **教师** | `Role.TEACHER` | 手机号+密码 | 托管班日常看板操作、课外课点名消课 | 看板 / 消课 两个工作页，按名下资源动态显示 |
| **平台管理员** | `Role.PLATFORM_ADMIN` | 手机号+密码 | 开通新机构、跨机构查看规模与到期状态、登记续费、维护机构联系人 | 独立的平台管理页（登录后整页替换，无法看到任何机构内部数据） |
| **家长**（隐性角色） | 无 | 无登录，凭 `share_token` 令牌链接/二维码 | 查看孩子的托管月度表现 *或* 课外课账户（二选一，取决于学生身份） | 公开分享页，无导航、无账号体系 |

**关键权限细节**：
- 机构管理员账号同时隐式持有"教师权限"——没有标注 `@PreAuthorize` 的教师类接口，管理员账号一样能调用成功。管理员在前端走的是专门的只读看板入口（`AdminKanbanController`，仅 GET，UI 带"只读"徽标），这是**前端路径设计**而非后端强制隔离，目前无实际漏洞但是隐式约定（见[功能全景与产品诊断 #09](../功能全景与产品诊断.md)）。
- 教师账号由管理员创建时可选角色（教师/管理员），即一个机构可以有多个 ADMIN 账号。
- 新建教师账号首次登录会被强制要求改密（`mustChangePassword` 标记），改密前无法进入系统任何其他页面。
- 机构的 `custodyEnabled` / `offCampusEnabled` 两个功能开关只影响管理后台侧边栏和教师端导航的**显示**，不是后端硬校验（目前风险低，接入对外 API 前需要补后端校验）。两个字段数据库默认都是 `TRUE`，**目前「基础配置」页面上手动切换这两个开关的 UI 已经隐藏**（`AdminSettingsModule.tsx` 的 `SHOW_BUSINESS_FEATURE_TOGGLES = false`）——因为现阶段接入的机构基本都同时需要托管和课外课，管理员暂时看不到、也不需要手动管这两个开关。

## 三、核心业务对象与关系

```
Institution（机构）
 ├─ custodyEnabled / offCampusEnabled（业务功能开关，两者不能同时关闭）
 ├─ validUntil（试用/订阅到期日，平台管理员维护）
 ├─ contactName / contactPhone / address（机构联系人，平台管理员维护，用于续费跟进）
 │
 ├─ Teacher（教师，1:N）—— role ∈ {ADMIN, TEACHER}
 │   └─ mustChangePassword（首登强制改密标记）
 │
 ├─ TeachingUnit（教学单元，1:N，由某个 Teacher 负责）—— 托管班和课外课的统一模型
 │   ├─ billingMode = MONTHLY   → 这是一个"托管班"
 │   └─ billingMode = LESSON_COUNT → 这是一个"课外课程"（含 lessonDurationMinutes / pricePerLesson）
 │
 ├─ Student（学生，1:N）
 │   ├─ teachingUnitId = NULL        → 纯课外课学生（无托管班）
 │   ├─ teachingUnitId = 某托管班ID  → 托管班学生（可能同时报名课外课 = 双重身份）
 │   └─ shareToken（建号时自动生成的 UUID，公开分享页凭此访问，终身不变）
 │
 ├─ StudentUnitEnrollment（学生-课外课报名关系，N:N，仅用于课外课）
 │
 ├─ ClassBillingRate（班级计费标准：月学费 + 日餐费，按托管班单独设置或批量设置）
 ├─ MonthlyBill（月度账单，按"学生+月份"生成，含学费/餐费/请假扣减快照/课外课附加费）
 │
 ├─ CourseConsumptionRecord / CourseRechargeRecord（课外课消课/充值流水——**任何报了课外课的学生都可以充值**，不区分是否同时在托管班，见[第五章](#五课外课计费与结算充值覆盖--月度账单兜底)）
 │
 ├─ InstitutionRenewalRecord（续费记录，平台管理员登记，plan ∈ {TRIAL, MONTHLY, HALF_YEAR, YEARLY}）
 └─ StudentShareViewLog（家长分享页查看日志，按"学生+自然日"去重，供平台管理员观察机构活跃度）
```

**关系要点**：
- `TeachingUnit` 是 2026-10 左右重构后的**统一模型**——以前托管班和课外课是两张表、两套权限模型（诊断 #05），现在合并为一张表，用 `billingMode` 区分，建单元/改派/启停/删除全部收归管理员统一管理。
- 学生的"身份"不是一个独立字段，而是由 `teachingUnitId` 是否为空 + 是否存在 `StudentUnitEnrollment` 记录两个条件推导出来的（见下表）。

| teachingUnitId | 课外课报名 | 身份 | 家长分享页看到什么 | 月度账单构成 |
|---|---|---|---|---|
| 非空 | 无 | 纯托管班学生 | 月度托管统计 | 学费 + 餐费 + 请假扣减 |
| 非空 | 有 | **双重身份** | 月度托管统计 + 当日课外课情况 | 学费 + 餐费 + 请假扣减 + 课外课未被充值覆盖部分的附加费 |
| 空 | 有 | 纯课外课学生 | 课外课账户对账单 | 学费/餐费记 0，只有课外课未被充值覆盖部分的附加费 |
| 空 | 无 | （极少见，刚建号未报名） | 空的课外课对账单 | 不生成账单（无任何消课/托管记录） |

> ⚠️ **容易搞错的点**：上表"月度账单构成"不是按身份二选一的两条路径，而是**同一套结算规则**（见[第五章](#五课外课计费与结算充值覆盖--月度账单兜底)）套用在所有学生身上——区别只在于有没有托管班决定要不要加学费/餐费。

## 五、课外课计费与结算：充值覆盖 + 月度账单兜底

> **2026-10-12 更正**：本节此前写成"纯课外课学生走充值/余额，托管班学生走月度账单附加费"的两条互斥路径，这个理解是错的，已核实并更正——**请以本节为准**。真实规则是：不管学生是否同时在托管班，课外课的充值和消课都走同一套结算逻辑；"是否有托管班"只决定月度账单里要不要额外加学费和餐费这两行，不影响课外课本身怎么计费。

### 5.1 统一结算规则（`CourseAccountService.classifyConsumptions`）

1. **任何报了课外课的学生都可以充值**——不要求"必须没有托管班"才能充值。`CourseRechargeRecord`（充值）和 `CourseConsumptionRecord`（消课）都是按"学生+课程"记录的，和这个学生是否同时是托管班学生无关。
2. **每次消课，系统会判断它当时有没有被充值余额"覆盖"**：把该学生在这门课上的全部充值和消课事件按时间顺序回放，从余额 0 开始——充值加课时数，每次消课先看当前余额是否 >0（>0 则这条消课"被覆盖"，余额照常扣 1；≤0 则这条消课"未被覆盖"）。
3. **被覆盖的消课**：相当于已经用充值余额付过钱了，**不会**再出现在月度账单里。
4. **未被覆盖的消课**：会在**月底生成月度账单时**，按该课单价汇总成一行"课外课附加费"，计入这个学生当月的账单。

也就是说：一个学生如果给某门课足额充值，当月消课都会被余额覆盖，月度账单上这门课的附加费是 0；如果没充值或充值不够，超出余额的部分会自动变成账单上的一笔待收费用——**充值是"预付"，月度账单是兜底收费机制，两者不冲突、不互斥**。

#### 5.1.1 补充值追溯抵扣（2026-10-13 新增，产品诊断 #54）

第 2 条的"按时间顺序回放"有一个反直觉的后果：**充值没法倒着覆盖它日期之前已经发生的消课**。如果学生先欠了几次课外课费用（没充值就消课了），账单按未覆盖全额生成之后，管理员才给他补充值，哪怕补的课时够还是不够，`classifyConsumptions` 严格按时间顺序算出来的结果依然是"未覆盖"——因为这笔充值记录的时间戳晚于那些消课发生的日期。实际发生过一次真实反馈：孙三欠了 7 次语文课（560 元），管理员事后补充值 10 次，重新生成账单却发现金额还是 560 元没变，而"对账单"弹窗里看到的余额（充值合计-消课合计，不分时间先后）已经是正数了——两处"余额"口径不一致，让人以为是 bug。

现在生成/重新生成账单时（`BillGenerationService.computeCourseConsumptionRows`），对这类按时间顺序判定"未覆盖"的消课，**只要这门课到目前为止的净余额（充值合计-消课合计，不分时间先后）已经转正或欠得更少了，就认为后续充值已经把欠费补上了**：
- 净余额 ≥0：这次账单这门课的应收金额按 **0** 计算。
- 净余额仍为负：只收差额部分（比如欠 7 次只补了 3 次，按剩下 4 次计费）。
- 不管是否被这样"追溯抵扣"，**消课次数和具体日期始终如实记录在账单明细里**，不会因为金额变成 0 就消失——管理员仍然能看到"这个月确实上了几次课"。

**但只在这个月账单还没标记"已缴费"时生效**：如果机构已经收过这笔现金（账单标过已缴费），之后再补充值也不会让已生成的账单金额倒着往回退，否则会出现"钱已经收了，账单却被后续充值免单"的双重优待。

**已知局限（没有做成通用 FIFO 账本）**：这里用的是"全部历史净余额"这种简化判断，只对"先欠费、后一次性补值"这种最常见场景是准确的。如果充值和消课来回交替得比较复杂（比如多次零散充值穿插在多次消课之间），这个净余额快照可能和"严格按时间顺序、一笔笔核账"的结果出现细微偏差。目前机构规模和实际使用场景下这个简化是够用的，如果后续业务对账精度要求更高，需要做一套更严谨的分账/核销机制（例如给每笔消课记录标记"被哪笔充值核销"），那是一次更大的改造，不在这次范围内。

### 5.2 托管班是否影响课外课计费？—— 不影响计费逻辑，只影响账单还要不要加别的

| | 纯托管班学生 | 纯课外课学生 | 双重身份学生 |
|---|---|---|---|
| 能否给课外课充值 | 不适用（没报课外课） | 可以 | 可以 |
| 课外课消课的计费规则 | 不适用 | 和左边"双重身份"完全一样：按 5.1 的覆盖规则 | 按 5.1 的覆盖规则 |
| 月度账单里有没有学费/餐费 | 有 | 没有（记 0） | 有 |
| 月度账单里有没有课外课附加费 | 没有（没报课外课） | 有（未覆盖部分） | 有（未覆盖部分） |

**关键结论：纯课外课学生也会生成月度账单**，只是这份账单的学费、餐费固定是 0，只统计当月课外课里"没被充值余额盖住"的部分，按单价算出金额列进账单。账单管理页专门有一个"纯课外课学生"筛选项（`AdminBillingModule.tsx`），"一键生成本月全机构账单"也会把这类学生一起生成（`BillGenerationService.generateBillsForInstitution` 遍历全机构所有在读学生，不区分是否有托管班）——这是 2026-10 教学单元合并时顺带修复的（原来按班级遍历会漏掉没有班级的纯课外课学生，见[诊断 #03](../功能全景与产品诊断.md)）。

### 5.3 家长分享页展示口径和结算口径不是一回事

虽然结算规则已经统一，但**家长分享页目前仍然按身份展示不同内容**：
- 纯课外课学生：看到完整的课外课账户对账单（已充值/已消耗/余额）。
- 双重身份学生：只看到一张轻量的"当日课外课情况"卡片（有没有上课、上了什么课），**不展示充值/余额信息**（`getCourseActivity` 当前的实现注释仍然写着"这类学生从不预充值，余额概念不成立"——这句注释已经和 5.1 的实际充值规则不一致，代码待排期修正，这里先记录这个已知的代码注释/文档不一致点，不代表产品决策）。

机构内部的定价治理：托管班的学费/餐费和课外课单价现在都统一在"定价中心"管理（2026-10-03 前课外课单价曾错放在教学单元管理页，已修复统一入口，见[诊断 #04](../功能全景与产品诊断.md)）。

## 六、机构生命周期与商业模式

```
平台管理员开通机构（设置试用到期日，默认建议 30 天）
        ↓
机构处于 TRIAL（试用）期 —— 机构管理员自行搭建教师/教学单元/学生，正常使用全部功能
        ↓
到期前 7 天内 → 机构列表状态徽标变为 EXPIRING_SOON（橙色，"N天后到期"）
        ↓
平台管理员联系机构 → 登记续费记录（选套餐 MONTHLY/HALF_YEAR/YEARLY）→ 机构 validUntil 更新 → 状态恢复 ACTIVE
        ↓（若未续费）
到期后 → 状态变为 EXPIRED（红色，"已过期N天"）—— 目前到期不会自动封禁功能，仅作平台管理员的可见提醒
```

商业模式要点（详见 memory：[[project_monetization_strategy]]）：
- **机构端**：固定订阅制付费（试用 → 月付/半年付/年付），本系统目前只做"登记"不做自动扣费/支付网关对接。
- **家长端**：不直接向家长收费，核心诉求是通过分享页/海报引导家长关注机构的公众号（非付费转化点），`StudentShareViewLog` 的查看次数统计即服务于这个增长指标。
- 首个真实试用机构已于 2026-09-02 上线，生产库从此有真实业务数据（见 memory：[[project_first_pilot_institution]]）。

## 七、技术栈速览

> 深度技术架构（部署、测试基建、环境变量、目录结构）留待后续专门文档，这里只给方向。

- **后端**：Spring Boot 3 + 原生 JDBC（无 JPA）+ MySQL 8.0 + Flyway 版本化迁移（当前最新 `V27`）+ Spring Security（JWT）。
