# 机构数据批量导入

给新入驻机构（或者首个试用机构补录历史数据）用的结构化模板 + 转换脚本。系统本身
目前没有任何自助导入功能（这块在 backlog 里），这套脚本是过渡方案：机构把数据按
模板整理好，技术负责人在本地把模板转换成 SQL，拿到生产环境手动执行。

## 整体流程

1. **生成空白模板**（一次性，模板本身不常变，生成过一次之后可以直接复用这个文件发给机构）：

   ```bash
   pip3 install -r requirements.txt   # 只需要 openpyxl + bcrypt
   python3 generate_template.py 机构数据导入模板.xlsx
   ```

2. **机构负责人（或者你自己照着机构给的手写/零散数据）填写模板**：三个 sheet——
   教师、教学单元（托管班+课外课）、学生，具体规则见模板里的"说明"页。

3. **转换成 SQL**：

   ```bash
   python3 import_to_sql.py 填好的模板.xlsx --admin-phone 13800001234 -o import.sql
   ```

   `--admin-phone` 填这批数据要导入到哪个机构的**管理员登录手机号**——用这个手机号
   在执行 SQL 时动态查出 `institution_id`，不需要你提前手动查数据库拿真实的机构
   自增 id。

   脚本会先把模板内部能查出来的问题（必填项缺失、格式不对、引用的临时编号不存在、
   同类型教学单元名称重复、手机号在模板内部重复等）一次性列出来，有问题就不会生成
   SQL；都通过了才会在当前目录生成 `import.sql`。

4. **执行前先看一遍 `import.sql`**，确认人数/数据看起来对；然后**务必先备份**：

   ```bash
   cd <仓库根目录>
   ./deploy/backup.sh --mysql-only
   ```

5. **在生产环境执行**（这一步，以及前面涉及生产服务器的所有操作，都由你自己手动
   做，不会由 Claude 代劳）：

   ```bash
   docker compose -f docker-compose.yml -f docker-compose.prod.yml exec -T mysql \
     mysql -uroot -p"$MYSQL_ROOT_PASSWORD" <数据库名> < import.sql
   ```

   必须用支持 `DELIMITER` 的 `mysql` 命令行客户端（上面这条命令或者登录后 `source`
   文件路径都可以），**不要加 `--force` 参数**。

6. **执行结果只有两种**：
   - 顺利执行完，没有任何 `ERROR` 输出——说明全部数据已经写入，老师可以用手机号 +
     默认密码 `888888` 登录（会被强制要求改密）。
   - 中途报错（比如手机号找不到对应机构、或者某个老师手机号和生产库里已有数据
     冲突）——**不会有任何一条数据被写入**，整批操作在一个事务里，出错即整体回滚。
     改好模板、重新跑第 3 步生成新的 `import.sql` 再执行一次即可，不需要手工清理
     任何残留数据。

## 为什么这么设计

- **不需要提前知道机构的数据库 id**：生成的 SQL 包了一个存储过程，执行时先按
  `--admin-phone` 对应的手机号查 `institution_id`，查不到就直接报错中止，一条
  数据都不会写；查到了才继续插入，全程一次性完成，不需要你先单独查一次 id。
- **不需要给每个老师编密码**：系统本身要求教师首次登录必须改密，初始密码内容不
  重要，导入时统一设成 `888888`（已验证：Python `bcrypt`（`rounds=10`）生成的
  哈希和后端 `Spring Security BCryptPasswordEncoder` 的默认强度完全兼容）。
- **模板里不填机构信息**：一次导入只对应一个机构，机构通过 `--admin-phone`
  参数在脚本层面指定一次，不需要在表格每一行重复填。
- **全部包在一个事务里**：教师/教学单元/托管班计费/学生/课外课报名关系之间
  有严格的先后依赖（按这个顺序建），任何一步失败都不该留下"插了一半"的数据。
  已经实测验证过三种场景：正常导入成功、管理员手机号查不到时零写入、执行到
  中途撞见唯一约束冲突（比如老师手机号和生产库里已有数据重复）时整批回滚、
  不留残留。

## 局限 / 已知限制

- 模板内部的校验只能发现"模板自己内部"的问题（比如同一个模板里两个老师填了
  相同手机号），**无法提前发现"和生产库里已有数据冲突"的问题**（比如新导入的
  老师手机号和别的机构已有老师重复——教师手机号是全平台唯一，不是按机构唯一）。
  这类冲突会在真正执行 SQL 时被数据库唯一约束拦下来，安全地整体回滚，但不会在
  生成 SQL 这一步就提前告诉你。如果担心这类冲突，执行前可以自己查一下：
  ```sql
  SELECT phone FROM teacher WHERE phone IN ('手机号1', '手机号2', ...);
  ```
- 同理，教学单元（托管班/课外课）的"同类型名称不能重复"这条规则，系统里只是
  应用层校验（没有数据库唯一约束兜底），脚本也只检查模板内部有没有重名。如果
  目标机构在生产库里已经手动建过同名同类型的教学单元，批量导入会**悄悄插入一个
  重名的教学单元，不会报错也不会回滚**——这一点和手机号冲突不是一回事（手机号
  冲突有数据库约束兜底，能安全回滚；这个没有）。执行前如果不确定，自己查一下：
  ```sql
  SELECT name, billing_mode FROM teaching_unit WHERE institution_id = <目标机构id>;
  ```
- 生成的 SQL 是直接操作数据库，不会经过应用层的机构功能开关校验
  （`institution.custody_enabled`/`off_campus_enabled`，默认都是开启状态）。
  如果目标机构关闭了托管班或课外课功能，用这套脚本仍然能导入对应类型的数据，
  不会像走正常接口那样被挡住——正常情况下（功能开关保持默认开启）没有影响。
- 这是一次性/半手工的过渡方案，不是正式的"导入功能"（没有 Web UI、没有机构
  自助上传入口）——这块已经记录在产品 backlog 里，等真的需要自助导入能力
  （比如机构数量变多、每次都要技术负责人介入变成瓶颈）时再评估要不要做。
- 只覆盖"老师 + 教学单元 + 学生"三类数据的首次建档，不处理后续的消课记录、
  充值记录、历史账单这些时间序列数据——如果机构还要补录这些历史流水，需要
  另外设计模板（不在这次范围内）。

## 文件说明

- `generate_template.py`：生成空白的 Excel 模板。
- `import_to_sql.py`：把填好的模板转换成 SQL。
- `requirements.txt`：Python 依赖。
